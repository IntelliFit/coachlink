# 支付宝支付流程说明

## 流程概览

1. **create**：创建订单并返回支付宝表单，前端跳转/展示支付宝付款页。
2. **notify**：支付宝服务器在用户付款后**异步 POST** 到 `notify_url`，**不依赖用户是否关闭页面**，是“已付款”的**主来源**。
3. **return**：用户付款后浏览器**同步跳转**到 `return_url`，用于跳转到“支付成功”页；同时做一次履约（幂等），防止 notify 延迟时用户已回到站内。
4. **query**：前端轮询查询订单状态；若查到已支付，同样做履约（幂等），用于用户未关页时的即时反馈。

## 万无一失原则

- **未付款**：只保留订单记录，不更新订阅、不更新教练钱包。
- **已付款**：必须保证（1）订阅状态/续费更新，（2）教练钱包入账。实现方式：
  - **主路径**：依赖 **notify**。用户扫码/付款后，支付宝会主动调我们的 notify，**即使用户立刻关掉页面也会执行**。
  - **兜底**：return（用户回到我们站点时）和 query（前端轮询）使用同一套履约逻辑，且全部**幂等**（`last_payment_order_id` / `related_order_id` 防重），多调几次不会重复加钱或重复开通。

## 共享履约逻辑

- 文件：`fulfillPaidOrder.ts`
- 内容：`fulfillSubscriptionOnPaid`（订阅/续费确认 + 教练站内信）、`updateTransactionAndWallet`（教练钱包入账 + 流水）。
- 调用方：notify、return、query 三者共用，保证行为一致且幂等。

## notify 验签

- 生产环境：验签失败必须返回 `fail`（400），支付宝会重试。
- 开发/本地：若使用 `mock_sign` 可放行，便于联调。

## 可选增强：定时补偿查询

若担心极少数情况（如 notify 请求失败、我方服务短暂不可用），可增加定时任务：对 `alipay_orders` 中 `status=pending` 且创建时间在近 24 小时内的订单，调用支付宝 `alipay.trade.query`，若已支付则调用同一套 `fulfillPaidOrder` 逻辑（幂等安全）。
