# 百度地图位置服务集成 - 产品需求文档 (PRD)

## 1. 背景与目标
为了促进 CoachLink 平台的“同城化”发展，增强教练与学员的线下连接，并为街头健身（Streetlifting）爱好者提供便捷的场地寻找工具，我们计划引入**百度地图服务**。

**核心目标：**
*   **促进线下连接**：通过地理位置匹配，帮助学员发现身边的教练，促进线下教学或交流。
*   **优化推荐体验**：在教练推荐算法中引入“距离”权重，优先推荐同城或距离更近的教练。
*   **增强工具属性**：完善“单杠地图”功能，不仅展示位置，更提供直接导航能力，解决“找不到地方”的痛点。

---

## 2. 用户故事 (User Stories)

### 2.1 学员 (用户)
*   "作为一名想找教练的学员，我希望能优先看到**离我比较近（同城）**的教练，这样我有机会与教练进行面对面的训练或交流。"
*   "在浏览教练列表时，我想直观地看到**教练离我大概多远**（例如 '5.2km'），以便我评估线下见面的可行性。"
*   "作为一名街头健身爱好者，我想在地图上查找附近的**单杠/训练点**。"
*   "当我找到一个感兴趣的单杠地点时，我希望点击一个按钮就能**直接唤起地图导航**过去，而不是需要手动复制地址再去地图搜。"

### 2.2 教练
*   "作为教练，我希望设置我的**常驻教学地点/城市**，以便同城的潜在学员更容易搜索到我。"
*   "我希望能展示我的详细训练场馆位置（如果有），吸引附近的学员。"

---

## 3. 详细功能需求

### 3.1 核心模块一：地理位置基础服务 (Infrastructure)
此模块是所有上层功能的基础。

#### 3.1.1 用户位置获取
*   **触发时机**：
    *   用户首次进入“寻找教练”页面或“单杠地图”页面时，请求定位权限。
    *   用户手动点击“定位”图标时。
*   **权限处理**：
    *   若用户允许：通过浏览器/百度 SDK 获取精确经纬度 (Lat/Lng)。
    *   若用户拒绝：
        *   **降级方案 1**：尝试通过 IP 定位获取大概城市（可选）。
        *   **降级方案 2**：提示用户手动选择当前城市（下拉选择省/市）。
*   **数据存储**：
    *   前端：通过 Context 或 LocalStorage 缓存用户当前位置，避免重复询问。
    *   后端（可选）：如果用户登录，可询问是否更新其 User Profile 中的常驻地（需用户确认）。

#### 3.1.2 教练位置管理
*   **教练端设置**：
    *   在“个人中心 / 编辑资料”中增加位置设置模块。
    *   **字段**：
        *   **常驻城市**（必填）：省/市/区联动选择。
        *   **详细地址**（选填）：如“朝阳公园南门”。
        *   **位置标注**（交互）：提供一个小地图，教练可在地图上点选精确位置，自动回填经纬度。
*   **数据结构**：
    *   更新 `coaches` 表，增加 `latitude`, `longitude`, `city`, `address` 字段。

---

### 3.2 核心模块二：同城教练匹配与展示 (Discovery)

#### 3.2.1 距离计算与排序
*   **后端逻辑**：
    *   输入：当前用户的经纬度。
    *   逻辑：实时计算数据库中所有教练与用户的直线距离。
    *   排序：支持按“距离最近”排序。
*   **前端展示**：
    *   在教练卡片（Coach Card）上显眼位置展示距离标签。
    *   **显示规则**：
        *   < 1km: 显示 "1km内" 或具体数百米。
        *   1km - 100km: 显示具体公里数，如 "5.2km"。
        *   > 100km: 可根据同城判定显示 "同城" 或仅显示城市名（如 "北京市"）。
        *   无定位权限：不显示距离，仅显示教练所在城市。

#### 3.2.2 筛选功能
*   增加 **"只看同城"** 开关/Tab。
*   开启后，仅展示 `coach.city === user.currentCity` 的教练。

---

### 3.3 核心模块三：单杠地图与导航 (Streetlifting Hub)

基于现有的 `streetlifting-index/locations` 页面升级。

#### 3.3.1 列表页优化
*   **距离展示**：不仅展示地点信息，同样展示离用户当前的距离。
*   **排序优化**：默认按距离由近到远排序，方便用户发现身边设施。

#### 3.3.2 一键导航 (Navigation)
*   **功能描述**：在地点卡片或详情页增加醒目的 **"去这里"** (或导航图标) 按钮。
*   **交互逻辑**：
    1.  点击按钮。
    2.  尝试唤起用户手机上已安装的地图 APP (百度地图 App 优先，或系统默认)。
    3.  若未安装 APP，自动跳转至百度地图 H5 网页版进行路线规划。
    4.  **参数传递**：必须准确传递目标地点的 `lat`, `lng`, `name` (地点名称), `address` (地址)，确保导航终点准确。

#### 3.3.3 地图模式 (可选/二期)
*   在列表页右上角增加“地图模式”切换。
*   进入地图模式后，全屏展示百度地图，将所有单杠点以 Marker 形式标注在地图上。
*   用户可视范围内的单杠点自动聚合或展示。

## 4. 技术与性能要求

### 4.1 性能
*   **数据库查询**：虽然增加了距离计算，但需优化 SQL 查询性能（使用 Spatial Index 或简单的 Lat/Lng 索引）。避免在每次列表加载时进行全表复杂的三角函数计算，可考虑预先按城市筛选再计算距离。
*   **SDK 加载**：百度地图 SDK 文件较大，必须使用 **懒加载 (Lazy Load)** 或 **异步加载** 策略，确保不影响首屏加载速度（LCP）。仅在用户进入相关页面时才初始化 SDK。

### 4.2 兼容性
*   **移动端优先**：重点适配 iOS Safari 和 Android Chrome 的地理位置权限申请交互。
*   **HTTPS**：浏览器 Geolocation API 必须在 HTTPS 环境下才能工作（本地 localhost 除外）。确保生产环境强制 HTTPS。

### 4.3 隐私与合规
*   **权限申请文案**：在申请定位权限时，必须清晰告知用户用途（“用于推荐附近的教练和场地”）。
*   **数据脱敏**：
    *   教练的详细定位：在前端展示时，除非教练明确公开详细地址，否则建议只显示“大致距离”或“商圈/街道级别”，避免精确到门牌号的隐私泄露（视业务策略定，如果教练愿意公开工作室地址则无妨，如果是个人住址则需注意）。

---

## 5. 验收标准 (Acceptance Criteria)

1.  **用户定位**：用户在授权后，系统能获取并 console 输出正确的经纬度。
2.  **教练列表**：
    *   在有定位权限时，教练列表能正确显示“xx km”。
    *   排序功能正常，近距离教练排在前面。
3.  **单杠导航**：
    *   点击“去这里”，在手机上能成功唤起百度地图 APP 或跳转网页导航页面。
    *   导航终点名称显示正确（不是显示“未知地点”）。
4.  **无权限处理**：在用户拒绝定位时，页面不报错、不白屏，UI 优雅降级（不显示距离，但显示城市）。
