# APP 与微信小程序功能对齐审计（2026-08-01）

## 1. 结论先行

APP 已经不是空壳：手机号/邮箱登录、验证码登录、训练执行基础记录、动作与计划、训练历史、教练发现、知识内容、街头力量核心功能、教练内容/定价/钱包、功率分析上传与轮询等主入口都已有实现。

但 APP 目前还不能称为与小程序“功能等价”。真正影响上线可用性的差异，不是少几个页面，而是以下闭环仍断裂或只完成了基础版：

1. **角色闭环有逻辑错误**：只要用户 `is_coach=true`，APP 就强制进入教练端；小程序以 `primary_role` 为准，并支持学员/教练切换。
2. **购买闭环没有完成**：APP 会创建支付订单并进入等待页，但没有真实调用原生微信支付 SDK；会员购买、教练订阅、续费都无法在 APP 内完成付款。
3. **今日训练只迁了很薄的一层**：APP 只取一个 `coachPlan || selfPlan` 并直接打开推荐 Day；小程序的多教练订阅、教练/自主计划切换、周/月历、顺延与补练、轻量任务、完成状态、分享等均未同步。
4. **训练执行缺少日常高频能力**：APP 有力量组记录和临时加组/加动作，但缺轻量任务、备注、PR、组视频、后台安全休息计时、训练反馈、完整总结与分享海报等。
5. **教练带训工作台不完整**：教练能看学员列表，但还不能在 APP 内完成小程序已有的学员计划查看/编辑/分配、1RM 批量维护、反馈处理和计划执行追踪。
6. **工具箱差异明显**：最新小程序已有 5 个 APP 没有的工具——单手引体评估、指尖光膜、接豆派对、引体冲刺、俯卧撑突围。
7. **原生能力底座尚未建立**：当前依赖和权限中没有相机、定位、地图、音视频播放、媒体相册保存、WebView、微信登录/支付、姿态识别等完整能力。

因此，近期不建议按“页面逐个搬运”推进，而应先把 **分支基线、角色、支付、训练、教练带训** 五个闭环补齐，再做内容体验和体感工具。

## 2. 审计基线与方法

### 2.1 Git 基线

本次已重新获取远端引用，没有切换分支、没有合并，也没有改动现有业务代码。

| 范围 | 审计基线 | 说明 |
| --- | --- | --- |
| 小程序 dev | `origin/dev` = `610a748d6fd77f8ed1ed8c8e669f2d5d4d9f07e7` | 2026-07-31，包含延后完善体能档案、APP 离线训练恢复、小程序功率下载/音频状态等较新改动 |
| 小程序 main | `origin/main` = `f77d43aecdd738f75d51b19d94eae6670b37d711` | 2026-07-31，包含指尖光膜导出付费等 main 独有改动 |
| 当前工作区 | `codex/dev-workspace-20260720` / `12e703db` | 保留了用户已有的 APP 训练缓存等未提交改动 |

`origin/main...origin/dev` 当前为 **main 独有 5 个提交、dev 独有 14 个提交**。两个分支不是简单的“dev 一定更新”或“main 一定更新”：

- `dev` 更新：延后完善体能档案、APP 离线训练恢复、功率分析下载/音频状态恢复、内容与场景修复等。
- `main` 更新：指尖光膜导出付费、公开下载地址、生产发布记录等。
- 两边最新路由清单相同，但个别实现文件不同；功率分析、引导、知识书籍、工具箱等不能只看一个分支。

**本报告的小程序目标基线采用 `origin/dev ∪ origin/main` 的功能并集。** 在正式开发前，必须先确定一个权威集成分支，否则会出现“刚同步到 APP，又被另一分支回退”的问题。

APP 基线采用：

- 当前工作区可见实现；
- 对照 `origin/dev` 中比当前分支更新的 APP 文件；
- 对未提交/未纳入当前分支的能力明确标记，不把它误算成稳定发布能力。

### 2.2 扫描范围

本次逐项检查了：

- 小程序最新路由、小程序页面、服务层、训练缓存工具；
- APP 导航栈、全部 screen 文件、API 调用、缓存、原生配置和依赖；
- `dev/main` 分叉文件及最新提交；
- 显式的“迁移中 / 后续补齐 / 暂不支持 / 承接页”等代码标记；
- 训练、教练、知识、工具箱、街头力量、支付、社交、设置等业务闭环。

这是一次**源码级静态审计**。未执行真实微信支付、相机姿态识别、地图、生产账号数据和真机交互，因此：

- “代码明确不存在/明确为占位”结论置信度高；
- “已有接口但真实服务端契约是否完全可用”仍需开发阶段联调确认；
- 页面视觉与真机兼容性不在本次结论内。

## 4. 详细差异

### 4.1 分支和工作区：先解决“同步目标是谁”

当前不能直接说“小程序最新就是 dev”或“就是 main”。两者都包含对方没有的最新能力。

另外，当前工作区的 APP 训练相关文件有用户未提交改动，`todayTrainingCache.ts` 在当前分支视角下还是新增文件，而 `origin/dev` 也有自己的版本。涉及文件包括：

- `apps/mobile/src/screens/TrainingScreen.tsx`
- `apps/mobile/src/screens/training/TrainingExecutionScreen.tsx`
- `apps/mobile/src/screens/training/ImpromptuTrainingScreen.tsx`
- `apps/mobile/src/screens/training/trainingCache.ts`
- `apps/mobile/src/screens/training/todayTrainingCache.ts`
- `apps/mobile/src/api.ts`
- `apps/mobile/src/config.ts`
- `apps/mobile/app.json`

开发前必须先做一次**三方合并审阅**：当前工作区 vs `origin/dev` vs `origin/main`。不能用覆盖式 checkout，也不能假设当前未提交文件等同于 dev 版本。

### 4.2 登录、引导和角色

#### APP 已有

- 手机号/邮箱 + 密码登录；
- 验证码登录、注册、找回密码；
- 滑块验证、访客入口；
- 个人资料、体能卡编辑；
- `origin/dev` 已加入“可延后完善体能档案”的提示与缺失字段统计。

#### 与小程序的差异

1. APP “手机号一键登录”实际调用 `handleWechatPlaceholder`，仅提示改用密码/验证码；没有微信 Open Platform 登录。
2. 没有小程序 `student-onboarding` 的完整多步骤流程：头像昵称、性别、身高体重、目标、水平、目标部位、每周频率、器械、训练时长等。
3. 没有小程序 `/api/user/switch-role` 的 APP 实现和入口。
4. APP 根导航用 `user.is_coach === true || primary_role === 'coach'` 判断教练模式。这会让“已获教练资格、但当前选择学员身份”的用户无法进入学员端。
5. 没有小程序的 `wechat-auth` 桥接及微信绑定状态闭环。
6. 设置页缺账号注销；小程序已调用 `studentService.deleteAccount` 并要求不可恢复操作二次确认。

#### 风险

- 角色逻辑是数据正确但 UI 角色错误的高风险缺陷，应先于一般页面迁移处理。
- 微信小程序的 JSAPI 支付身份与原生 APP 支付身份不是同一种 OpenID/订单参数，不能直接把小程序支付参数复制到 APP。

### 4.3 今日训练首页

#### APP 已有

- 读取本地今日训练缓存后异步拉云端；
- 调用 `/api/plan-lib/get-today-training-instance`；
- 选择 `data.coachPlan || data.selfPlan`；
- 展示当前计划、推荐天数、训练日数；
- 直接进入推荐 Day；
- 提供即兴训练、动作库、计划历史、训练历史、e1RM 入口；
- 当前工作区已补 60 天、按用户隔离的基础缓存。

#### 小程序已有、APP 未同步

- 多个有效教练订阅与教练切换面板；
- 教练计划 / 自主计划模式切换；
- 访客公共首页；
- 周日历、展开月历、选中日期；
- 计划动态排期、延迟、日期碰撞、实际完成日展示；
- `missingDays` 补练和跳过；
- 休息日状态；
- DIET / CARDIO / HABIT 轻量任务的新建、编辑、删除和完成；
- 正确的当前 Day / 历史 Day / 未来 Day 可执行和只读判断；
- 进行中训练继续入口；
- 订阅宽限与续费提示；
- 计划完成弹窗、更新档案、生成下一计划、全部计划；
- 今日整体打卡图与训练成果分享；
- 更完整的计划进度和模块完成度。

#### 关键设计差异

APP 缓存当前只保存单个 `activeInstanceId + todayPlan + actions + executionsByDayIndex`。小程序缓存还保存教练订阅集合、选中教练、教练/自主模式、不同计划块、选中日期、完成日期、缺失 Day 等。若只继续在现有简化结构上加字段，容易形成第二套不兼容缓存；应先把领域模型对齐，再扩 UI。

### 4.4 训练执行

#### APP 已有

- 计划训练和即兴训练两种模式；
- 本地快照快速展示，再向云端拉取；
- 重量、次数、RPE 记录；
- 完成组；
- 添加/删除额外组；
- 添加/删除额外动作；
- 完成整次训练；
- 训练后进入分享页；
- 接口成功后更新执行快照和今日训练缓存。

#### 小程序已有、APP 未同步

**P0 必须补：**

- DIET / CARDIO / HABIT 的 `complete-item`；
- 云端真实 `in_progress` 覆盖错误本地只读状态；
- 当前 Day、历史预览、未来预览的权限与强制刷新规则；
- 即兴训练本地进行中恢复和 `/api/impromptu/current` 兜底；
- 失败阶段、空 execution、重试与重新开始处理；
- 快照完整保存 execution、planInstance、actions，而不是只返回 execution。

**P1 体验对齐：**

- 每组备注；
- 手动 PR、自动 PR 与纪录展示；
- 每组选择/上传/粘贴/预览视频；
- 已完成组再次编辑；
- 后台安全的绝对截止时间休息计时，支持 ±10 秒、跳过、最小化；
- 默认重量继承、步进调整和更细校验；
- 训练难度与文字反馈给教练；
- 完成总结：总容量、动作统计、肌群热图；
- 训练分享海报生成与保存；
- 动作详情/视频入口；
- 多选动作与器械/肌群筛选。

### 4.5 即兴训练

APP 已能加载个人动作和公共动作、搜索选择并创建即兴训练，属于真实功能。但仍缺：

- 打开页面先恢复最近一条本地进行中即兴训练；
- 本地没有时调用云端 `/api/impromptu/current`；
- 只允许适用的力量动作，避免非组次动作进入当前执行 UI；
- 器械、肌群筛选；
- 动作图片与详情；
- 单动作快捷开始；
- 公共动作库入口和来源统计；
- 快照中持久化动作详情。

### 4.6 计划、动作和训练历史

这部分不应重做，APP 已有不少可复用基础：

- 个人/公共动作库、复制、基础编辑；
- 计划列表、计划历史、计划详情；
- 训练历史日历、汇总与详情接口；
- e1RM 趋势；
- 训练分享页。

仍需同步的重点：

- 动作视频真实播放，而不是只复制/显示 URL；
- APP 端动作媒体上传；
- 完整计划编辑器对训练日和四类项目的结构化编辑；
- 与小程序相同的计划导入/解析与校验；
- 历史和结果分享海报的保存/系统分享闭环。

### 4.7 会员、教练订阅与支付

#### APP 已有

- 会员页、会员状态、配额、推荐奖励；
- 教练套餐、问卷、预支付流程；
- 创建平台微信支付订单；
- 支付等待页轮询订单状态；
- 购买记录和购物车基础流程。

#### 断点

- `PaymentWechatScreen` 明确是说明页；
- `PaymentWebviewScreen` 也是说明页；
- 订单返回的支付参数没有交给原生 SDK；
- 续费入口明确提示“支付桥接还在迁移”；
- 教练市场的购买入口导航到占位网页支付页；
- APP 没有微信 Open Platform 的原生登录/支付配置与回调处理；
- 当前依赖中没有微信支付 SDK 或桥接模块。

#### 正确实现边界

原生 APP 支付不能复用小程序 `wx.requestPayment` 的 JSAPI 参数。需要：

1. 微信开放平台 APP 资质、Android 包名/签名、iOS Bundle ID 与 Universal Link 配置；
2. 服务端增加或确认 APP 支付下单契约；
3. Expo custom dev client / 原生模块接入；
4. 支付结果回调、前后台恢复、深链、取消/失败/重复支付处理；
5. 订单状态仍以服务端查询为最终事实；
6. 会员购买、首次订阅、续费、问卷后购买共用同一支付编排。

### 4.8 教练发现和教练详情

APP 已有教练搜索、方向筛选、价格、内容、订阅状态、问卷和 AI 生成计划入口，主体不是空壳。

差异包括：

- `reviewCount` 会展示，但评价 Tab 没有请求评价列表，即使数量大于 0 仍显示“暂无评价数据”；
- 联系邮箱、电话、社交链接的复制/拨打/打开能力不足；
- 申请材料主要以文本展示，图片/视频预览不完整；
- 教练内容的视频媒体没有完整播放器；
- 已订阅用户续费未闭环；
- 支付失败后恢复、重试和返回来源处理不完整。

### 4.9 教练工作台

#### 已有且应保留

- 教练总览；
- 视频审核；
- 学员列表和基础详情；
- 动作、内容、计划模板 CRUD；
- 定价；
- 问卷管理；
- 自动化；
- 收入；
- 钱包余额、待结算、流水、提现；
- 汇付商户开户，含身份证图片和银行卡资料。

- `expo-camera` / 姿态识别或 MediaPipe；
- `expo-location`；
- `react-native-maps` 或其他地图组件；
- `expo-video` / `expo-audio`；
- `expo-media-library`；
- `react-native-webview`；
- 微信 Open Platform 登录/支付原生桥接。

这意味着体感游戏、真实地图、知识音视频、保存分析视频、原生支付不能只写 React 页面，需要先做 native capability epic。

## 8. 开发验收与测试门禁

后续每个同步任务至少覆盖：

1. **身份**：游客、普通学员、有教练资格但当前学员角色、当前教练角色；
2. **网络**：首次无缓存、已有缓存、弱网、接口失败、重新进入；
3. **生命周期**：刷新/重启、前后台切换、支付或媒体 App 往返；
4. **数据幂等**：重复点击、重复进入、断网恢复不重复创建订单/execution/分配；
5. **缓存**：用户隔离、60 天裁剪、云端覆盖本地、退出登录不串数据；
6. **支付**：成功、取消、失败、超时、服务端已成功但客户端回调丢失；
7. **平台**：Android/iOS 权限拒绝、永久拒绝、系统设置返回、地图/相册差异；
8. **数据库清理**：自动化创建的账号、计划、订单、execution 等必须在 `finally` 清理。

按照仓库现有门禁，涉及代码的后续实现仍需执行 lint、typecheck、test；直接涉及登录/会话、订阅支付或计划 API CRUD 时还应运行相应 E2E。APP 原生功能必须用 Android 真机/模拟器和 iOS 构建分别验证，不能以 Expo Web 结果代替。

## 9. 不建议重复开发的部分

以下能力已经有真实基础，应优先修入口或补闭环，不要推倒重做：
