# 测试价值与分工说明

> 回答两个核心疑问：
> 1. E2E测试是否"强行依赖业务逻辑"？
> 2. 单元测试主要测API，但API本身一般都不会有什么问题？

---

## 🎯 核心结论

### E2E测试确实依赖业务逻辑，但这是它的价值所在

**E2E测试的本质**：模拟真实用户操作，验证"用户可见的行为"是否符合预期。

- ✅ **优点**：能抓到"新功能把老功能改坏"（回归问题）
- ⚠️ **代价**：业务逻辑变了，测试也要跟着改（这是正常的，不是bug）

### 单元测试的价值不只是"API不出错"

**单元测试的本质**：验证复杂的业务规则、边界条件、权限控制等**纯逻辑**。

- ✅ **优点**：快速、稳定、能覆盖大量边界情况
- ✅ **价值**：特别是像"credits计算"这种复杂业务规则，必须用单元测试保证正确性

---

## 📊 两种测试的分工（什么时候用哪个？）

### 场景1：Credits计算逻辑（应该用单元测试）

**业务逻辑**：
- 对外卖"4周计划"，对内扣减"训练日credits"
- 线下迁移：`start_execution_day > 1` 时，之前的训练日也要计入已消耗
- 窗口截断：如果计划只有2周，4周订阅的窗口要截断到2周

**为什么用单元测试？**
- 这是**纯函数**，不依赖数据库、不依赖UI
- 有大量边界情况需要覆盖（迁移场景、窗口截断、去重等）
- 如果逻辑改错了，会导致**财务问题**（多扣或少扣credits）

**实际例子**（`src/lib/subscriptionCredits.test.ts`）：

```typescript
it("computeUsedCredits includes offline consumed credits before startExecutionDay (migration)", () => {
  // 测试：线下迁移场景
  // 学员从第8天开始（线下已完成前7天）
  // 应该把前7天中的训练日计入已消耗
  const used = computeUsedCredits({
    eligibleTrainingDayIndexSet: scope.eligibleTrainingDayIndexSet,
    executions: [], // 没有线上执行记录
    startExecutionDay: 8, // 从第8天开始
  });
  expect(used).toBe(3); // 前7天有3个训练日，应该计入
});
```

**如果这个逻辑改错了**：
- ❌ E2E测试可能测不出来（因为E2E只验证"剩余X天"显示，不验证计算细节）
- ✅ 单元测试能立即发现（直接验证计算逻辑）

---

### 场景2：注册后问卷弹窗（应该用E2E测试）

**业务逻辑**：
- 新用户注册后，应该自动弹出问卷
- 问卷填写完成后，才能继续使用

**为什么用E2E测试？**
- 这是**用户可见的行为**（弹窗出现/不出现）
- 涉及多个系统协作（注册API → 前端路由 → 问卷组件 → 状态管理）
- 如果改坏了，用户**立即就能看到**（体验问题）

**如果只有单元测试**：
- ✅ 可以测试"注册API返回成功"
- ✅ 可以测试"问卷API能获取问卷"
- ❌ **但测不到"注册后弹窗是否真的出现"**（这是前端逻辑）

**如果只有E2E测试**：
- ✅ 能测到"注册后弹窗出现"
- ❌ 但测不到"credits计算是否正确"（这是后端纯逻辑）

---

### 场景3：订阅状态显示（E2E + 单元测试配合）

**业务逻辑**：
- 订阅创建时：`start_date=null` → 显示"制定中"或"未开始"
- 第一次训练后：`start_date` 被写入 → 显示"剩余X天"
- "剩余X天"的计算依赖credits逻辑

**测试策略**：

1. **单元测试**（`subscriptionCredits.test.ts`）：
   - 验证credits计算逻辑是否正确
   - 验证边界情况（迁移、窗口截断等）

2. **E2E测试**（`e2e/b1-subscription.spec.ts`）：
   - 验证"制定中"vs"未开始"的UI显示
   - 验证"剩余X天"的UI显示
   - 验证训练执行后状态更新

**为什么两者都需要？**
- 如果credits计算错了 → 单元测试能发现
- 如果UI显示逻辑错了 → E2E测试能发现
- 如果两者都对了，但集成有问题 → E2E测试能发现

## 🔍 你的疑问解答

### Q1: E2E测试是否"强行依赖业务逻辑"？

**答案：是的，但这是它的价值所在。**

**为什么依赖业务逻辑？**
- E2E测试验证的是"用户可见的行为"
- 用户行为 = 业务逻辑的外在表现
- 所以E2E测试必须知道"什么情况下应该显示什么"

**这是好事还是坏事？**
- ✅ **好事**：能抓到"新功能把老功能改坏"（回归保护）
- ⚠️ **代价**：业务逻辑变了，测试也要跟着改（这是正常的，不是bug）

**如何降低维护成本？**
1. **只测试P0核心流程**（不要什么都测）
2. **测试"用户可见的行为"**，而不是"内部实现细节"
3. **使用稳定的选择器**（如 `data-testid`，而不是依赖文案）

**例子**：
```typescript
// ❌ 不好的做法：依赖文案（文案改了测试就失败）
await expect(page.getByText("制定中").first()).toBeVisible();

// ✅ 更好的做法：使用稳定的选择器
await expect(page.getByTestId("subscription-status")).toHaveText("制定中");
```

---

### Q2: 单元测试主要测API，但API本身一般都不会有什么问题？

**答案：单元测试的价值不只是"API不出错"。**

**单元测试能测什么？**

1. **复杂的业务规则**（最重要的价值）
   - Credits计算（`subscriptionCredits.test.ts`）
   - 权限判断（谁能访问什么）
   - 状态转换（什么条件下状态会变）

2. **边界条件和错误处理**
   - 空值、null、undefined
   - 负数、0、超大数
   - 并发、竞态条件

3. **API的输入验证**
   - 参数缺失、类型错误
   - 权限不足（401、403）

**为什么说"API本身一般都不会有什么问题"？**
- 如果API只是"CRUD"（增删改查），确实没什么好测的
- 但如果API包含**复杂业务逻辑**，就必须用单元测试保证正确性

**实际例子**：

```typescript
// ❌ 如果只有E2E测试，这个bug可能测不出来
it("should not allow coach to access other coach's students", async () => {
  // 测试：教练A不能访问教练B的学员数据
  const res = await POST(req, { coachId: "coach-b-id" });
  expect(res.status).toBe(403);
});
```

**如果这个权限逻辑改错了**：
- ❌ E2E测试可能测不出来（因为E2E只验证"正常流程"，不验证"异常情况"）
- ✅ 单元测试能立即发现（直接验证权限逻辑）

---

## 📋 测试策略建议

### 优先级1：核心业务规则 → 单元测试

**必须用单元测试覆盖**：
- ✅ Credits计算（`subscriptionCredits.test.ts`）
- ✅ 权限判断（谁能访问什么）
- ✅ 状态转换（订阅状态、计划状态等）
- ✅ 数据验证（参数校验、类型检查）

**为什么？**
- 这些是**纯逻辑**，不依赖外部系统
- 如果改错了，会导致**业务问题**（财务、权限、数据一致性）
- 单元测试**快速、稳定**，能覆盖大量边界情况

---

### 优先级2：用户可见的行为 → E2E测试

**必须用E2E测试覆盖**：
- ✅ 注册后问卷弹窗
- ✅ 教练分配计划后学员端显示
- ✅ 训练执行后状态更新
- ✅ 支付流程（如果涉及UI）

**为什么？**
- 这些是**用户可见的行为**，涉及多个系统协作
- 如果改坏了，用户**立即就能看到**（体验问题）
- E2E测试能验证**端到端的流程**

---

### 优先级3：两者配合

**复杂场景需要两者配合**：
- ✅ 订阅状态显示（credits计算 + UI显示）
- ✅ 训练执行流程（业务规则 + UI交互）
- ✅ 支付流程（业务规则 + UI交互）

**为什么？**
- 单元测试保证**业务逻辑正确**
- E2E测试保证**用户可见的行为正确**
- 两者配合，能最大程度避免"新功能把老功能改坏"

---

## 🎯 总结

### E2E测试的价值
- ✅ 能抓到"新功能把老功能改坏"（回归保护）
- ✅ 能验证"用户可见的行为"（体验问题）
- ⚠️ 依赖业务逻辑（这是正常的，不是bug）

### 单元测试的价值
- ✅ 能验证**复杂的业务规则**（credits计算、权限判断等）
- ✅ 能覆盖**大量边界情况**（快速、稳定）
- ✅ 不只是"API不出错"，而是"业务逻辑正确"

### 最佳实践
1. **核心业务规则** → 单元测试（快速、稳定）
2. **用户可见的行为** → E2E测试（回归保护）
3. **复杂场景** → 两者配合（最大程度避免问题）
