## 1. 结论先行

当前项目没有一个“很好的一份测试文件能测出所有功能是否完善”。

现在已经有一个正确方向的雏形：

- `vitest.config.ts`：覆盖 `src/**/*.test.ts` 和 `tests/**/*.test.ts`。
- `playwright.config.ts`：有 `e2e/` 端到端测试，并带开发服务器启动配置。
- `src/app/api/test/e2e/seed/route.ts` 和 `cleanup/route.ts`：提供幂等测试数据准备和清理底座。
- `tests/ai/prompts/t3-agent-regression-prompt.md`：有一份 AI 回归测试指令文件。
- `docs/testing/如何将业务逻辑转化为测试.md`：已经明确提出“文档即规格，规则即测试，场景即 E2E”。

但它目前还只是“小骨架”，不是“全业务质量工具”：

- E2E 只有 3 个 spec 文件，主要覆盖登录会话、B1 订阅状态、学员个人计划 CRUD、教练模板 CRUD。
- 微信小程序没有对应的自动化 UI 测试文件。
- 支付、汇付分账、退款、教练工作台、训练执行复杂交互、聊天、知识库、街健、会员、购物车等核心域没有成体系的回归覆盖。
- UI 自动化大多依赖文案和 placeholder，几乎没有稳定的 `data-testid`。
- CI 里 `npm test || true` 和 E2E `continue-on-error: true` 说明测试报告会产出，但不会强制阻断。
- `scripts/pre-deploy-check.js` 里的构建检查实际跳过构建，不能当成真正上线门禁。
- `tsconfig.typecheck.json` 当前只 include 少量文件，不是全项目类型门禁。

所以更合理的目标不是写一个巨大的测试文件，而是做一个“单入口回归工具”：

```text
一个命令/一个测试协议入口
  -> 调用多份按业务域拆开的测试规格
  -> 共用 seed/cleanup/fixture ledger
  -> 输出统一报告
```

也就是说，用户使用上可以像“一个工具”，工程实现上必须拆分。

## 3. 为什么不建议写成一个巨大的测试文件

一个“测全功能”的巨型文件会有几个问题：

- 失败定位困难：一个 UI 文案或环境问题会让整条链路全红。
- 测试数据清理困难：支付、聊天、视频、计划、订阅、钱包等副作用交织后，很容易残留。
- 执行慢：全站 UI E2E 可能拖到几十分钟，开发者不会频繁运行。
- 维护成本高：任何页面文案调整都会牵动总文件。
- 不适合并行：独立业务域无法拆分运行。

正确形态应该是：

```text
tests/regression/
  business-map.md 或 scenario-registry.ts
  fixtures/
    seed.ts
    cleanup-ledger.ts
  web/
    auth-session.spec.ts
    student-training-spine.spec.ts
    coach-workstation.spec.ts
    payment-admin.spec.ts
  api/
    subscription-credit.spec.ts
    payment-safety.spec.ts
    chat.spec.ts
  weapp/
    student-training.weapp-spec.ts
    auth-review-safe.weapp-spec.ts
  ai/
    agent-regression-prompt.md
```

对外再提供一个统一命令：

```bash
npm run test:regression:core
```

这样用户感觉是“一个工具”，工程上仍然是模块化规格。

## 4. 业务逻辑沉淀方法

建议先把每个业务域沉淀成同一种格式，再转测试代码。

每条业务规则至少包含：

```text
规则 ID：
业务域：
适用端：Web / 微信小程序 / API / 管理后台
角色：游客 / 学员 / 教练 / 管理员
前置条件：
用户动作：
系统响应：
数据写入：
本地缓存写入：
副作用：
清理方式：
测试类型：unit / API / web E2E / weapp E2E / AI prompt
优先级：P0 / P1 / P2
```

判断用什么测试：

- 纯计算：单元测试。
- 状态转换：单元测试 + API 测试。
- 用户可见行为：E2E。
- 跨端缓存：小程序自动化 + API 检查。
- 支付/分账/退款：优先 API/集成测试，网关必须 mock 或沙盒，不允许真实资金。
- 内容、知识、聊天：API + 最小 UI 流程。

### 5.1 认证、会话、角色

- 小程序个人中心、消息入口未登录时跳转登录。

### 5.2 学员今日训练主链路

必须沉淀的规则：

- 有 active 订阅但无计划：显示“教练计划正在制定中”，可联系教练或即兴首练。
- 有 active 订阅且有计划但未开始：显示“未开始/开始训练”口径。
- 订阅处于宽限期：显示续费提醒和宽限期剩余天数。
- 多个教练订阅：优先展示有计划的订阅，用户选择的订阅应持久化。
- 有教练计划和自建计划：可切换“教练计划/我的计划”。
- 今日训练页主卡片优先展示当前应做什么。
- 周视图/月视图只能辅助导航，不能覆盖主行动。
- 休息日展示恢复/轻任务，不应强迫进入力量训练。
- `missingDays` 存在时提供补练/跳过，不强行拉回过去。
- 训练执行通知未确认时必须先展示确认弹层。
- 已完成当天训练后返回今日页，进度应立即反映。
- 小程序优先读取本地缓存，再由云端覆盖。
- 云端数据与本地不一致时，云端为准。
- 小程序今日页缓存 key 为 `today_training_page_cache_v1`，60 天过期。

当前覆盖：

- B1 订阅状态和 start/finish 后剩余天数。

缺口：

- 今日训练页 UI 主流程几乎未测。
- 小程序缓存和弱网体验未测。
- 多订阅/自建计划/宽限期/缺口补确认未测。
- 执行通知 gate 未测。

建议测试：

- `e2e/student-today-training.spec.ts`
- `wechat_app/tests/today-training-cache.weapp-spec.ts`
- `src/lib/planProgress.test.ts` 继续扩展 missingDays/skipped 规则。

### 5.3 训练执行页

必须沉淀的规则：

- 计划模式进入执行页前，未确认 execution notice 必须先确认。
- 直接深链进入执行页也不能绕过 notice。
- 即兴训练不需要计划 notice。
- 只读历史记录不能触发写操作。
- 开始训练应复用已有 in_progress execution。
- 过久未完成的 execution 应提示继续/完成/稍后。
- 力量组必须记录必要字段，允许编辑已完成组。
- RM/% 强度下缺少 1RM 时应提示校准。
- 完成组后应计算 e1RM/PR。
- 组间休息计时器离开页面再回来应恢复。
- 视频可以本地上传，也可以贴链接。
- 新增组、新增动作、删除额外动作必须只影响当前 execution。
- 饮食/有氧/习惯等轻任务有独立完成逻辑。
- 计划模式完成组/项后必须同步执行快照和今日页缓存。
- 即兴训练只写执行快照，不写今日训练计划映射。
- 完成整日后可跳过反馈，也可提交反馈给教练。
- 分享路径/打卡图不应破坏训练完成状态。

当前覆盖：

- B1 E2E 通过 API start/finish 覆盖了最短路径。
- `executionProgress.test.ts` 覆盖一点进度计算。

缺口：

- Web 训练执行复杂交互没有 UI E2E。
- 小程序训练执行没有 UI E2E。
- 休息计时器、视频、PR、反馈、额外动作、缓存写入未测。

建议测试：

- `e2e/training-execution-core.spec.ts`

- `wechat_app/tests/training-execution-cache.weapp-spec.ts`
- `tests/api/execution/*.test.ts`

- 教练能查看学员列表、搜索、分页、排序。

### 5.5 订阅、支付、汇付分账、退款

必须沉淀的规则：

- 订阅订单金额必须由服务端定价决定，不能信任客户端 amount。
- 续费只能续当前订阅产品，不能在续费中暗中切换套餐。
- Web Alipay、微信小程序 WeChat/Huifu 支付创建订单时，应写入正确 order_type、payment_provider、requires_huifu_split。
- 支付回调必须验签。
- 支付回调/主动查询必须校验网关金额等于本地订单金额。
- 浏览器 return URL 不能更改金钱或履约状态。
- notify、query、sync-pending 必须共用幂等履约逻辑。
- 汇付分账订单在没有 split detail 前不能给教练钱包入账。
- `coach_subscription_settlements` 是远程分账幂等账本。
- `processing` 不能盲目重试真实转账，必须先查询原请求。
- split_failed 可由管理员显式处理。
- Huifu/WeChat/split-required 订单不能走直接 Alipay refund。
- 退款必须先网关正确退款，再本地回滚钱包/平台收入。
- 管理后台必须展示 payment_provider、trade status、settlement status。

当前覆盖：

- 未看到成体系的支付/分账测试。
- 状态文件里记录过大量支付修复，但测试未同步覆盖。

缺口：

- 这是当前最高风险区之一。
- 需要 mock 网关响应或沙盒，不应该在 E2E 中打真实资金接口。

建议测试：

- `tests/api/payment/payment-amount-authority.test.ts`
- `tests/api/payment/alipay-fulfillment-idempotency.test.ts`
- `tests/api/payment/huifu-split-ledger.test.ts`
- `tests/api/payment/refund-safety.test.ts`
- `e2e/admin-payment-visibility.spec.ts`

### 5.8 微信小程序特有规则

必须沉淀的规则：

- 主包首页 `/pages/index/index` 与旧今日训练路径语义一致。
- 底部导航按角色切换，学员端为训练/发现/工具箱/消息/个人，教练端为概览/点评/学员/计划库/我。
- 消息和个人中心未登录时跳登录。
- 今日训练页本地缓存优先，云端覆盖。
- 训练执行页快照优先，云端覆盖。
- `today_training_page_cache_v1` 和 `training_execution_snapshots_v1` 均遵循 60 天规则。
- 训练中写操作成功后，同步执行快照和今日页缓存。
- 即兴训练不写今日页计划 execution 映射。
- WeChat 头像/昵称只能用户主动授权，不阻塞注册。
- 登录页必须可返回首页，不强迫授权。

当前覆盖：

- 没有小程序自动化测试文件。
- 只有 `wechat_app/package.json` 的 build/dev 脚本。

缺口：

- 这是产品当前主体验面，必须补自动化或至少补 AI 测试协议。

建议测试：

- `wechat_app/tests/auth-review-safe.weapp-spec.ts`
- `wechat_app/tests/today-training.weapp-spec.ts`
- `wechat_app/tests/training-execution.weapp-spec.ts`
- `wechat_app/tests/coach-workstation.weapp-spec.ts`

## 8. 建议的单入口回归工具

### 8.1 命令设计

```json
{
  "scripts": {
    "test:regression:core": "node scripts/run-regression-core.mjs",
    "test:regression:web": "playwright test e2e/core",
    "test:regression:api": "vitest run tests/api src/lib",
    "test:regression:weapp": "node wechat_app/scripts/run-weapp-regression.mjs",
    "test:regression:ai": "vitest run tests/ai"
  }
}
```

### 8.2 分层

- Level 1：纯逻辑快速测试，几秒级。
- Level 2：API 合同和数据库幂等，分钟级。
- Level 3：Web 关键 E2E，分钟级。
- Level 4：微信小程序关键 E2E，需要 DevTools/模拟器。
- Level 5：支付沙盒/网关 mock，单独运行，默认不碰真实资金。

### 8.3 输出

统一生成：

- `test-results/regression/summary.json`
- `test-results/regression/report.html`
- 失败截图。
- 创建数据和清理数据 ID 对照。
- 环境信息：branch、commit、baseURL、数据库名或环境标记。

## 10. 对用户问题的直接回答

如果你的目标是“有没有一个现成文件可以测出所有功能是否完善”，答案是：现在没有。

如果你的目标是“做一个像工具一样的总回归入口”，答案是：可以做，而且当前项目已经有 seed/cleanup、Vitest、Playwright、AI Prompt 的基础。

最正确的路线是：


这件事值得做，而且会很长。它本质上不是“写一个测试文件”，而是把 CoachLink 的业务真相整理成一套可执行规格。
