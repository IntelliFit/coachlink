# 如何将业务逻辑文档转化为测试代码

> 目标：把 `docs/done/core-business/` 下的业务逻辑文档，转化为可执行的测试代码，确保"文档即规格"。

---

## 🎯 核心思路

**业务逻辑文档 = 测试用例的输入**

1. **从文档中提取规则** → 转化为测试用例
2. **从文档中提取场景** → 转化为E2E测试
3. **从文档中提取边界条件** → 转化为单元测试

---

## 📋 转化步骤（三步走）

### 第一步：识别文档中的"可测试规则"

在业务逻辑文档中，寻找以下模式：

#### ✅ 可测试的规则类型

1. **"必须"、"应该"、"不能"** 等强制性规则
   - 例：`订阅创建时不算开始` → 测试：`start_date 应该为 null`
   - 例：`第一次训练 start 时写入 start_date` → 测试：`首次 start 后 start_date 应该被写入`

2. **计算公式/算法**
   - 例：`totalCredits = 在 subscribed_weeks 窗口内统计训练日数量` → 测试：`4周计划，每周3练，totalCredits 应该为 12`

3. **状态转换规则**
   - 例：`start_date=null → 显示"未开始"` → 测试：`UI 应该显示"未开始"`

4. **边界条件**
   - 例：`如果计划只有2周，4周订阅的窗口要截断到2周` → 测试：`2周计划，4周订阅，窗口应该截断到2周`

5. **异常情况处理**
   - 例：`线下迁移：start_execution_day > 1 时，之前的训练日也要计入已消耗` → 测试：`从第8天开始，前7天的训练日应该计入已消耗`

---

### 第二步：选择测试类型（单元测试 vs E2E测试）

| 文档规则类型 | 应该用哪种测试 | 为什么 |
|------------|--------------|--------|
| **计算公式/算法** | 单元测试 | 纯函数，不依赖外部系统 |
| **状态转换规则** | 单元测试 + E2E测试 | 业务逻辑（单元测试）+ UI显示（E2E测试） |
| **用户可见的行为** | E2E测试 | 涉及多个系统协作 |
| **边界条件** | 单元测试 | 快速、稳定，能覆盖大量情况 |
| **异常情况处理** | 单元测试 | 直接验证逻辑，不依赖UI |

---

### 第三步：编写测试代码

#### 模板1：从文档规则到单元测试

**文档规则**（来自 `business-logic-b1-subscription-plan-execution.md`）：
```
### 1.2 订阅什么时候算"开始"？
- 订阅创建时不算开始（学员付费≠开始训练）
- 学员第一次真正开始训练时才开始：在 POST /api/execution/start 首次执行时写入 coach_subscriptions.start_date
```

**转化为单元测试**：

```typescript
// tests/api/execution/start.test.ts
describe("订阅开始时机", () => {
  it("订阅创建时 start_date 应该为 null", async () => {
    // 1. 创建订阅
    const subscription = await createSubscription({
      studentId: "student-1",
      coachId: "coach-1",
      subscribedWeeks: 4,
    });
    
    // 2. 验证：start_date 应该为 null
    expect(subscription.start_date).toBeNull();
  });

  it("第一次执行 start 时应该写入 start_date", async () => {
    // 1. 创建订阅（start_date = null）
    const subscription = await createSubscription({...});
    
    // 2. 第一次执行 start
    await POST("/api/execution/start", {
      instanceId: instance.id,
      dayIndex: 1,
    });
    
    // 3. 验证：start_date 应该被写入
    const updated = await getSubscription(subscription.id);
    expect(updated.start_date).not.toBeNull();
    expect(new Date(updated.start_date).getTime()).toBeCloseTo(Date.now(), -3);
  });
});
```

```typescript
test("订阅状态显示：start_date=null 时应该显示'未开始'", async ({ page }) => {
  // 1. 准备数据：创建订阅，但不开始训练（start_date = null）
  const s = await seed(page.request, { 
    withPlan: true, 
    subscribedWeeks: 4 
  });
  
  try {
    // 2. 登录学员账号
    await login(page, { 
      phone: s.student.phone, 
      password: s.student.password 
    });
    
    // 3. 访问订阅页面
    await page.goto("/coach/subscription");
    
    // 4. 验证：应该显示"未开始"
    await expect(page.getByText("未开始").first()).toBeVisible();
    
    // 5. 验证：不应该显示"剩余 X 天"（因为还没开始）
    await expect(page.getByText(/剩余\s+\d+\s+天/)).not.toBeVisible();
  } finally {
    await cleanup(page.request, s);
  }
});
```

## 📚 实际例子：从文档到测试

### 例子1：Credits计算规则

**文档**（`business-logic-b1-subscription-plan-execution.md`）：
```
### 3.1 credits 的"总量"怎么算？（totalCredits）
1) 将 subscribed_weeks 换算为计划天数窗口：
   - window = [1, subscribedWeeks*7]
   - 再用 plan 最大 dayIndex 截断（计划不足 N 周时）

2) 在这个 window 中统计 training_days 里 type=training 的天数，得到 totalCredits
```

**已实现的测试**（`src/lib/subscriptionCredits.test.ts`）：

```typescript
it("computes totalCredits within first N weeks window (3 sessions/week, 4 weeks)", () => {
  const trainingDays = makePlan({ weeks: 8, sessionsPerWeek: 3 });
  const scope = computeCreditsScope({
    trainingDays,
    startExecutionDay: 1,
    subscribedWeeks: 4,
  });
  // 4周，每周3练 = 12 credits
  expect(scope.totalCredits).toBe(12);
  expect(scope.scopeStartDayIndex).toBe(1);
  expect(scope.scopeEndDayIndex).toBe(28);
});

it("caps window by plan max dayIndex", () => {
  const trainingDays = makePlan({ weeks: 2, sessionsPerWeek: 4 }); // 只有14天
  const scope = computeCreditsScope({
    trainingDays,
    startExecutionDay: 1,
    subscribedWeeks: 4, // 要求28天，但计划只有14天
  });
  // 应该截断到14天
  expect(scope.scopeEndDayIndex).toBe(14);
  // 2周 * 4次 = 8 credits
  expect(scope.totalCredits).toBe(8);
});
```

**转化过程**：
1. ✅ 识别规则：`window = [1, subscribedWeeks*7]` → 测试窗口范围
2. ✅ 识别规则：`用 plan 最大 dayIndex 截断` → 测试截断逻辑
3. ✅ 识别规则：`统计 type=training 的天数` → 测试总数计算

### 例子2：线下迁移规则

**文档**（`business-logic-b1-subscription-plan-execution.md`）：
```
### 1.5 线下迁移怎么处理？
使用 coach_plan_instances.start_execution_day 表示"学员已经线下完成到哪里"，并且：
- 不插入假 execution（不污染执行表）
- credits 扣减会把 start_execution_day 之前的训练日视为已消耗（线下也算训练次数）
```

**已实现的测试**（`src/lib/subscriptionCredits.test.ts`）：

```typescript
it("computeUsedCredits includes offline consumed credits before startExecutionDay (migration)", () => {
  const trainingDays = makePlan({ weeks: 8, sessionsPerWeek: 3 });
  const scope = computeCreditsScope({
    trainingDays,
    subscribedWeeks: 4,
    startExecutionDay: 8, // 从第8天开始（线下已完成前7天）
  });
  
  // 前7天有3个训练日（第1、2、3天），应该计入已消耗
  const used = computeUsedCredits({
    eligibleTrainingDayIndexSet: scope.eligibleTrainingDayIndexSet,
    executions: [], // 没有线上执行记录
    startExecutionDay: 8,
  });
  expect(used).toBe(3); // 前7天有3个训练日
});
```

**转化过程**：
1. ✅ 识别规则：`start_execution_day 之前的训练日视为已消耗` → 测试扣减逻辑
2. ✅ 识别规则：`不插入假 execution` → 测试：executions 为空，但 usedCredits 仍包含迁移前的训练日

### 例子3：训练执行规范

**文档**（`training-execution-self-consistent-spec-v1.md`）：
```
## 一、拍板结论（必须遵守）
- **拍板 1：允许跳过训练日**
  - 学员可以在未完成某些训练日的情况下继续后续训练日。
  - 系统应提供"补漏/补确认/标记跳过"的闭环，但**不应该**把用户强制拉回到过去。

- **拍板 2：未开始的训练日不显示日期**
  - 仅对"已开始/已完成"的训练日显示真实日期（来源于时间戳）。
  - 未开始训练日不展示"计划日期/预计日期"，避免与真实执行冲突。
```

**应该写的测试**（目前还没有，建议添加）：

```typescript
// e2e/training-execution.spec.ts
test("允许跳过训练日：学员可以跳过第1天，直接训练第2天", async ({ page }) => {
  const s = await seed(page.request, { withPlan: true });
  try {
    await login(page, { phone: s.student.phone, password: s.student.password });
    
    // 1. 访问今日训练页
    await page.goto("/today-training");
    
    // 2. 跳过第1天（如果有跳过按钮）
    await page.getByTestId("skip-day-1").click();
    
    // 3. 开始第2天训练
    await page.getByTestId("start-day-2").click();
    
    // 4. 验证：第2天可以正常开始（不应该被强制回到第1天）
    await expect(page.getByText("第2天训练")).toBeVisible();
  } finally {
    await cleanup(page.request, s);
  }
});

test("未开始的训练日不显示日期", async ({ page }) => {
  const s = await seed(page.request, { withPlan: true });
  try {
    await login(page, { phone: s.student.phone, password: s.student.password });
    await page.goto("/today-training");
    
    // 1. 验证：未开始的训练日不应该显示日期
    const day1Card = page.getByTestId("training-day-1");
    await expect(day1Card.getByText(/\d{4}-\d{2}-\d{2}/)).not.toBeVisible();
    
    // 2. 开始第1天训练
    await page.getByTestId("start-day-1").click();
    
    // 3. 验证：已开始的训练日应该显示真实日期
    await expect(day1Card.getByText(/\d{4}-\d{2}-\d{2}/)).toBeVisible();
  } finally {
    await cleanup(page.request, s);
  }
});
```

## 🛠️ 实践指南

### 步骤1：阅读业务逻辑文档

找到 `docs/done/core-business/` 下的文档，例如：
- `business-logic-b1-subscription-plan-execution.md`
- `training-execution-self-consistent-spec-v1.md`
- `coach_plan_system_design.md`

### 步骤2：提取可测试规则

在文档中标记：
- ✅ **"必须"、"应该"、"不能"** → 强制性规则
- ✅ **计算公式** → 算法规则
- ✅ **状态转换** → 状态规则
- ✅ **边界条件** → 边界规则

### 步骤3：选择测试类型

- **纯逻辑/计算** → 单元测试（`tests/**/*.test.ts`）
- **用户可见的行为** → E2E测试（`e2e/*.spec.ts`）
- **两者都有** → 两者都写

### 步骤4：编写测试代码

参考模板：
- **单元测试模板**：参考 `src/lib/subscriptionCredits.test.ts`

### 步骤5：验证测试覆盖

运行测试，确保：
- ✅ 所有规则都有对应的测试用例
- ✅ 边界条件都有覆盖
- ✅ 异常情况都有处理

## 🎯 总结

### 核心原则

1. **文档即规格**：业务逻辑文档 = 测试用例的输入
2. **规则即测试**：每个"必须"、"应该"规则都应该有对应的测试
3. **场景即E2E**：每个用户场景都应该有对应的E2E测试

### 转化公式

```
文档规则 → 识别规则类型 → 选择测试类型 → 编写测试代码 → 验证覆盖
```
