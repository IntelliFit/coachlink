## 5. 测试用例规范与用例集

### 5.0 一段话把“智能导入”说清楚（用于对齐团队口径）

智能导入的目标不是“把文本直接变成几组几次”，而是：**先识别“这是什么动作”以及“这个动作属于哪种类型、应该具备哪些属性（字段）”，再基于文本为这些属性填值**；当某些属性在原文里缺失或不确定时，系统必须进入**确认/兜底**（用 `null` / “自选” 让用户后续补齐，而不是瞎猜）。导入阶段的动作匹配 **只在用户私有动作库**里进行（不自动匹配公共动作库）。后续的“带条件/带问卷（one-filter）”属于增强能力，可暂不纳入导入链路。

> 这段话建议在评审/对外说明时直接使用。

### 5.1 目标

智能导入的最大风险来自“文本千奇百怪 + AI 不确定性”。要让功能稳定、成本可控，需要把**可确定的部分**变成可回归测试的规则：

- 全局说明分离（`splitPlanGlobalPreface`）
- 动作名清洗（`sanitizeActionName`）
- “未显式给次数时如何处理 reps”的规则（取决于该动作是否启用“次数”属性）
- 休息日的保留与补齐规则

同时补充两类“更贴近业务本质”的测试目标（你提到的难点）：

- **动作类型表征**：同一个“动作名”在不同类型下，字段集合不同（例如力量 vs 计时力量 vs 有氧/饮食/习惯）。
- **属性缺失的兜底/确认**：缺了就留空（`null` / “自选”），并确保前端有确认/补齐入口。

### 5.1.1 动作类型与属性（用于写 expected 时的断言口径）

> 这一小节的作用：帮助写用例时知道“该断言什么”，避免把所有动作都当成 `sets×reps`。

- **力量（STRENGTH）- 非计时**
  - 典型字段：`sets`、`reps`、`restSeconds`、`intensityConfig`
  - 若该动作启用了“次数”属性（动作库 attrs 包含“次数”），但原文缺少次数：应为 `null` / “自选”（例如只写 10RM 没写次数 → `reps=null`，让用户后续补齐，而不是瞎猜）
- **力量（STRENGTH）- 计时/静力**
  - 典型字段：`sets`、`durationSeconds`、`restSeconds`、`intensityConfig`（常为 null）
  - 关键点不是“reps 必须为 null”，而是**该动作应启用“持续时间”属性、并可不启用“次数”属性**（动作库 attrs 不包含“次数”）。这样前端不会要求输入 reps，计划里也不会出现“伪造次数”。
  - 技术表现上：如果系统仍输出了 `reps=null`，也是可接受的（表示“无次数/不适用”）；测试断言应优先检查“attrs 与 durationSeconds”而非死盯 reps 字段。
- **有氧（CARDIO）/饮食（DIET）/习惯（HABIT）**
  - 当前系统在模板编辑器里允许使用 `custom_data` 表征（并允许 `actionId` 为空）
  - 导入链路若暂不支持端到端结构化：最低要求是不污染动作名、不崩溃；未来支持时应把内容落到 `custom_data` 并保留可编辑入口。

### 5.1.2 属性配置“模板”（Profiles）优先于自由生成（推荐方向）

> 你指出的关键点：动作 attrs 应该“很自由”，但**自由的最好方式不是让模型随便造 attrs**，而是让模型从少量稳定的“配置模板”里选。
>
> 这样可以显著降低：
> - 解析波动（同一动作今天输出 `次数`，明天输出 `持续时间`）
> - UI 不一致（某次导入突然要求填 reps，某次不要求）
> - 测试难度（断言口径更稳定）

建议至少内置两种覆盖面最大的 profile（后续可扩展）：

- **Profile A：次数型力量（COUNT_STRENGTH）**
  - attrs：`["组数", "次数", "强度", "休息时间"]`
  - 适用：绝大多数常规力量动作（深蹲/卧推/划船/弯举/引体等）
  - 规则：若原文没写次数，则 `reps=null`（不猜；交给用户后续补齐/自选）
- **Profile B：计时型力量（TIME_STRENGTH）**
  - attrs：`["组数", "持续时间", "休息时间"]`（通常不含“次数”）
  - 适用：悬挂/支撑/保持/计时类动作（平板支撑、悬垂、静止保持等）
  - 规则：用 `durationSeconds` 表达；`reps` 不适用（可省略或保持 null），测试应优先断言 attrs 与 durationSeconds

> 测试口径建议：用例里优先断言“动作选择了哪个 profile”（attrs 组合），而不是死盯某个字段是不是 null。

### 5.2 用例文件组织

所有用例放在 `docs/智能导入计划/cases/`：

- `case-XXX-input.txt`：用户输入（原始文本）
- `case-XXX-expected-actions.json`：阶段 1 期望（动作提取结果的关键点）
- `case-XXX-expected-template.json`：阶段 2 期望（模板结构关键点）

说明：

- 这里的 expected 不要求写全量字段，建议只写“必须稳定”的字段（例如：休息日是否拆出并占位；计时动作是否落到 durationSeconds 且 attrs 不包含“次数”；RM-only 是否不猜 reps 等）。
- actionId 在测试里通常无法稳定（取决于数据库），建议用“动作名/逻辑断言”表达。

建议每个用例至少覆盖以下三类断言之一（越多越好）：

- **识别正确**：动作名不夹带强度/组次/休息；能区分计时 vs 非计时。
- **填值正确**：强度/组次/休息时间解析正确；缺失字段必须为 `null` / “自选”。
- **匹配范围正确**：只在私有动作库里做自动匹配；公共库不参与自动匹配（需要时通过“先加入公共动作到私有库”间接命中）。

### 5.3 建议的自动化方式（后续工程）

后续可加一个脚本（例如 `scripts/smart-import-regression.ts`）：

- 读取 `cases/` 下输入文本
- 调用内部纯函数（文本预处理、动作名清洗等）做单测
- 对需要 AI 的步骤：可以在 CI 里跑 “mock LLM 输出” 的方式，或只跑确定性部分

### 5.3.1 自动生成“真实用例留痕”（推荐，最贴近业务）

手写 `expected-*.json` 的问题是：很容易与真实 UI 行为脱节。为此我们提供一个“留痕模式”：你把文本直接丢进智能导入正常跑一遍，系统会把**输入、两阶段大模型的 prompt/原始输出、解析后的结构化结果、以及 UI 快照**写入到 `docs/`，自动形成一份可复现案例，你再在生成的 `case.md` 里补评论即可。

#### 开启方式（本地/自托管环境）

需要同时开启 **前端开关** 与 **后端开关**：

- `NEXT_PUBLIC_SMART_IMPORT_TRACE=1`（前端显示“保存为用例”开关）
- `SMART_IMPORT_TRACE=1`（后端允许写盘；默认关闭）

#### 生成位置

每次导入会生成一个目录：

- `docs/智能导入计划/cases-generated/<traceId>/`

#### 会保存哪些内容（核心文件）

- `stage1.*`：动作提取阶段（input/normalized/prompt/raw/parsed/postprocessed）
- `stage2.*`：模板解析阶段（splitPreface/per-week/prompt/raw/parsed/postprocessed/merged）
- `ui.snapshot.json`：前端在“确认动作/预览模板”时看到的数据快照\n+- `case.md`：自动生成的用例说明模板（留给你写评论）\n+- `meta.json`：时间戳与基础元信息\n+
#### 安全与限制（必须读）

- **会保存 prompt 和大模型原始输出**，其中可能包含：你的原始文本、私有动作库列表、以及任何你粘贴的敏感信息。\n+- 该功能依赖“服务端可写仓库目录”，因此 **仅适用于本地/自托管环境**；云部署/Serverless 可能不可写。\n+- 建议把 `cases-generated/` 加入 `.gitignore` 或在团队内约定“不提交含敏感信息的用例目录”。
