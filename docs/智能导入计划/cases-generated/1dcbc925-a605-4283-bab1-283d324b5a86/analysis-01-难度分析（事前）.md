## 案例难度分析（事前）

- traceId：`1dcbc925-a605-4283-bab1-283d324b5a86`
- 输入文件：`stage1.input.txt`（与 `stage2.input.txt` 同源）

### 1. 为什么这是“好样例 / 值得学习”

这份输入文本整体更“工程友好”，主要体现在：

- **训练日结构清晰**：`W1D1/W1D2/W1D3` 明确分段，休息日也单独成段（“休息1天/休息2天”）。
- **动作条目格式统一**：每条动作基本是 “动作名 + 组数 + 次数 + （可选：RM/组休/备注）”，不容易把多个动作黏在一起。
- **备注位置合理**：例如“可选：练后半小时…”被写成单独条目，更容易落到 `note`。
- **信息相对完备**：大多数动作都明确写了 sets 与 reps，强度也用 RM 表达，留给系统“猜”的空间更小。

### 2. 仍然存在的潜在难点（但风险较低）

- **括号内执行要点**：如 `负重引体（底部暂停）`、`（底部暂停+顶端暂停）`  
  - 风险：动作名与“变式要点”绑定，动作库是否有该变式决定匹配策略。
  - 期望：若私有库存在同名变式则精确匹配；否则回退到基础动作名，并把“暂停”写入 `note`（本案例中看起来私有库已存在对应动作，因此风险低）。

- **休息日多行内容**：如“拉伸、松解、低强度有氧 / 冷热交替洗澡…”  
  - 风险：容易被合并进前一天 `note` 或被丢失。
  - 期望：保留为独立 `type:"rest"` 天的 `dayNote`（本案例中表达清晰，风险低）。

- **可选动作/建议**：如“可选：练后半小时…”  
  - 风险：被误解析为必做结构化动作。
  - 期望：作为 `note` 保留（或在 UI 中标注为可选）。

### 3. 测试人员“应重点核对”的断言（建议）

- **休息日占位正确**：休息日必须生成独立 `rest day`，并且按自然日占用 dayOfWeek/dayIndex。
- **动作条目不丢失**：训练日里的每条动作都能落到 `actions[]`（含“可选建议”的 note）。
- **强度解析合理**：RM 写入 `intensityConfig.relativeIntensity`；组休分钟转为 `restSeconds`。
- **备注保留**：可选说明/注意事项应进入 `note` 或 `dayNote`，不应丢失。

### 4. 难度等级（主观评估）

- **整体难度**：中（更接近“标准输入”）
- **主要风险来源**：动作变式（括号暂停）与休息日多行说明的保留方式
