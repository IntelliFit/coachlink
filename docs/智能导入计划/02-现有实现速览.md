## 2. 现有实现速览（当前线上行为）

> 目标：让新同事在 10 分钟内理解“现在系统怎么跑起来的”，并能快速定位入口/数据结构。

### 2.1 两阶段解析（阶段 1/阶段 2）

> 命名对齐：本文会把 **Stage 1/Stage 2** 统一解释成中文口径，避免测试同学看英文文件名“眼花缭乱”。
>
> - Stage 1 = **动作识别**（识别“有哪些动作”，并尽量匹配私有动作库）
> - Stage 2 = **计划结构识别**（识别“第几周第几天/训练日还是休息日/每个动作的组次强度备注”，生成模板结构）

- **阶段 1：动作识别（parse-actions）**
  - 输入：用户粘贴的文本 `text`
  - 输出：动作列表（包含是否匹配已有动作、是否需要自动计算重量、是否包含自重、attrs 等）
- **阶段 2：计划结构识别（parse-template）**
  - 输入：原始文本 `text` + 用户确认后的动作列表 `actions`
  - 输出：`weeks` + `trainingDays[]` + `globalDescription?`

### 2.1.1 为什么“突然多了这么多预处理/后处理”？

从功能上看两阶段确实很简单：**阶段 1 提动作名，阶段 2 出结构化模板**。  
但真实输入非常“脏”，LLM 的输出也不总是严格可用，所以需要少量“确定性规则”把不稳定性压住：

- **预处理（preprocess）**：把“文本长相”变得更适合模型读取，减少模型把强度/休息/组次数当成动作名的一部分。
- **后处理（postprocess）**：把模型返回的 JSON 做确定性修正，保证：
  - 动作名尽量干净（强度/组次/组休不要混进动作名）
  - 只在**私有动作库**范围内复用动作（避免误用公共库/误新建重复）
  - 与你动作库里已有动作的配置保持一致（例如是否包含自重、是否自动算重量等）

这些步骤不是“额外复杂化”，而是为了让导入**更稳定、更可回归、更好 debug**。尤其是你现在做“真实用例留痕”，必须把每一步中间产物保存下来，才知道问题到底发生在：输入、prompt、模型、解析、还是后处理。

### 2.1.2 用例留痕文件：测试同学到底该看哪些？

> 结论先说：**大多数时候只需要看 3 个文件**（其余文件用于定位问题来源）。

- **必看（最常用）**
  - `stage1.postprocessed.json`：阶段 1 最终“动作列表”（用于动作确认）
  - `stage2.merged.json`：阶段 2 最终“模板结构”（用于预览与导入）
  - `ui.snapshot.json`：UI 当时展示/转换出来的数据（用来定位“后端对了但前端显示不对/反之”）
- **出现问题才看（定位链路在哪一步出错）**
  - `stage1.raw.txt` / `stage2.*.raw.txt`：模型原始输出（是否胡说/是否截断）
  - `stage1.parsed.json` / `stage2.*.parsed.json`：从 raw 里解析出的 JSON（解析成功了吗）
  - `stage1.prompt.txt` / `stage2.*.prompt.txt`：当时到底给模型喂了什么（规则是否正确/是否太长）
  - `stage1.normalized.txt`：预处理后的文本（是否把“黏连”拆开了）
  - `stage1.splitPreface.json` / `stage2.splitPreface.json`：全局说明拆分是否正确

### 2.1.3 阶段 1（动作识别）每一步具体在干什么？（带真实例子）

代码入口：`src/app/api/plan-lib/parse-actions/route.ts`  
预处理/后处理函数：`src/lib/planImportText.ts`

以下用你这次 trace 的真实片段举例（`traceId=1dcbc925-a605-4283-bab1-283d324b5a86`）。

#### Step A：`stage1.input.txt`（原始输入）

含义：就是你粘贴的文本，服务端收到后原样记录下来，用于复现。

示例（节选）：

```
W1D1
- 负重引体（底部暂停） 4组9次（使用11RM的重量）（组休4-5分钟）
```

#### Step B：`stage1.splitPreface.json`（全局说明拆分）

含义：把“第一条 W1D1/第一周 (W1) 之前的内容”当作全局说明（热身/注意事项），正文用于识别动作，避免热身里的动作/描述污染动作库。

为什么有用：你后面会把 `globalDescription` 写到模板/实例的描述里给学员看，同时阶段 1/2 的动作识别不会被热身“带歪”。

#### Step C：`stage1.normalized.txt`（预处理：把“黏连”拆开）

含义：做轻量文本规范化，让模型更容易把“动作名”和“强度 token（RM/%/kg/RPE）”分开。

对比示例（同一行，input vs normalized）：

- input：
  - `使用11RM的重量`
- normalized：
  - `使用 11RM的重量`

这类“插空格”的作用是：当输入出现 `负重引体5RM`、`用11RM`、`10kg引体` 这类黏连时，模型更不容易把 `5RM/11RM/10kg` 当成动作名的一部分。

#### Step D：`stage1.prompt.txt` + `stage1.raw.txt`（调用模型）

- `prompt.txt`：发给模型的“完整提示词”（包含：输出 JSON 约束、只用私有动作库匹配、动作名清洗规则等）
- `raw.txt`：模型原始输出（可能含多余文本/不完全 JSON —— 虽然我们已要求 JSON）

为什么要存：如果某次结果突然变差，第一时间要确认是：
- prompt 变了？（规则被改坏了/上下文变长被截断了）
- 模型输出变了？（被截断/格式不合规/胡说）

#### Step E：`stage1.parsed.json`（raw → parsed：能 JSON.parse 的版本）

含义：把 `raw.txt` 里的内容做“确定性解析”（清理 ```json fence、兜底截取 `{...}`），拿到一个可用的 JSON 结构。

代码：`src/lib/deepseek.ts` 的 `parseJsonResponse()`。

#### Step F：`stage1.postprocessed.json`（parsed → postprocessed：业务可用的最终动作列表）

含义：对模型给的动作列表做确定性后处理，保证“可用且与私有库一致”：

- **动作名清洗**：`sanitizeActionName()`（例如去掉括号里的说明/强度/组次等）
- **过滤非动作条目**：`isLikelyNonActionName()`（例如“休息1天”“组休3分钟”这种）
- **私有库匹配纠偏**：如果模型没填或填错 `matchedExistingId`，用相似度匹配补齐
- **去重合并**：同一个 existingId 或同名归一化后只保留一个，避免新建重复动作
- **以私有库配置为准**：如果匹配到已有动作，就用库里的 `includesBodyWeight/enableAutoWeightCompute/attrs` 覆盖模型猜测（避免“模型瞎猜导致动作配置漂移”）

真实例子（你这次 trace 里确实发生了变化）：

- 在 `stage1.parsed.json` 里：
  - `锤式弯举.needsAutoCompute = false`
- 到 `stage1.postprocessed.json`：
  - `锤式弯举.needsAutoCompute = true`

这不是“随便改”，而是因为 **匹配到了私有动作库中的同名动作**，后处理会用你库里该动作的 `enableAutoWeightCompute` 覆盖模型的判断（确保一致性）。

> 也因此：如果你发现某个动作的 `includesBodyWeight/needsAutoCompute` 在 postprocessed 里“不符合直觉”，优先检查**动作库里这条动作的配置**是否本来就设置错了——留痕正好把这个问题暴露出来。

### 2.1.4 阶段 2（计划结构识别）每一步具体在干什么？（带真实例子）

代码入口：`src/app/api/plan-lib/parse-template/route.ts`  
辅助函数：`src/lib/planImportText.ts`（`splitPlanGlobalPreface/findFirstLineForAction/lineHasExplicitReps`）

说明：阶段 2 **不会**像阶段 1 那样做 `normalizeTextForActionExtraction()`（插空格/拆黏连）。原因是阶段 2 需要尽可能保留原文细节（强度/备注/行内信息）来生成结构化字段与 note/dayNote。

以下同样用你这次 trace 举例（`traceId=1dcbc925-a605-4283-bab1-283d324b5a86`）。

#### Step A：`stage2.input.txt`（原始输入）

含义：阶段 2 实际吃进去的文本（通常就是你粘贴的全文），用于复现。

#### Step B：`stage2.splitPreface.json`（全局说明拆分）

含义：与阶段 1 一样，提取 `globalDescription`（热身/注意事项），正文 `bodyText` 用来做结构解析，避免说明污染训练日结构。

#### Step C：`splitPlanByWeekSections()`（按周拆分：为什么会出现 `week-1` 文件）

含义：把长文本按周切分成更短的片段，分别喂给模型，减少截断风险。

代码位置：`src/app/api/plan-lib/parse-template/route.ts` 里的 `splitPlanByWeekSections()`（支持 `W#D#` 和 “第X周/第一周”）。

留痕文件因此按周出现：

- `stage2.week-1.input.txt`：第 1 周片段的输入
- `stage2.week-1.prompt.txt` / `raw.txt` / `parsed.json` / `postprocessed.json`：第 1 周片段的中间产物

> 如果你的计划有 W1..W12，就会有 `week-1..week-12` 一整套文件。**这不是重复**，而是每周单独解析、最后再合并。

#### Step D：`stage2.week-1.prompt.txt` + `stage2.week-1.raw.txt`（调用模型）

与阶段 1 同理：

- `prompt`：完整提示词（规则、动作库 ID 列表、输出 JSON 约束）
- `raw`：模型原始输出

用途：定位“是不是模型胡说/截断/格式不合规”，或“是不是 prompt 规则写错”。

#### Step E：`stage2.week-1.parsed.json`（raw → parsed：能 JSON.parse 的版本）

含义：用 `parseJsonResponse()` 把 raw 转成 JSON 对象（清理 ```json fence + 兜底截取花括号）。

#### Step F：`stage2.week-1.postprocessed.json`（parsed → postprocessed：业务最终周结果）

阶段 2 的后处理比阶段 1 更偏“字段归一 + 兜底规则”，主要做 3 件事：

**F1. 强度字段归一（IntensityConfig 形态统一）**

模型可能输出 3 种不同形态：

- `{ type: "rm", value: 5 }`
- `{ type: "fixed", fixedWeight: 127.5 }`
- 或已经是我们希望的嵌套形态（`relativeIntensity/fixedWeight`）

后处理会统一成你们代码期望的结构（`relativeIntensity` / `fixedWeight: { value, unit }`），避免前端/DB 类型不稳定。

代码位置：`src/app/api/plan-lib/parse-template/route.ts` 约 L301-L350。

**F2. 禁止“猜 reps”（避免把 RM 当次数）**

核心规则：如果原文那一行 **没有明确写次数**，就 **reps 必须为 null**；计时动作（durationSeconds 有值）也必须 `reps=null`。

> 重要补充（与你截图的“动作属性”一致）：在你们系统里，每个动作的属性（attrs）是可选的，**计时/静力动作可以不勾选“次数(reps)”，只勾选“持续时间”**。  
> 因此从业务/前端视角更准确的口径是：
>
> - **若该动作 attrs 包含“次数”**：原文没写次数 → `reps=null`（不猜，交给用户后续补齐/自选）
> - **若该动作 attrs 不包含“次数”（典型：计时动作）**：前端不会要求 reps；此时 `reps` 字段即使存在也应视为“不适用”（可省略或保持 `null`），测试断言应优先看 `durationSeconds` 与 attrs（是否启用“持续时间”）。

实现方式：

- 用 `findFirstLineForAction(section.text, actionName)` 找到该动作在原文中的第一行
- 再用 `lineHasExplicitReps(line)` 判断这一行是否真的写了次数（如 `4×8`、`3组8次`、`10次` 等）
- 如果没写，就把模型输出的 reps 清空（`reps=null`），防止“5RM → 5次”的灾难性误判

代码位置：`src/app/api/plan-lib/parse-template/route.ts` 约 L355-L377。

> 你这次 W1 文本里每个动作基本都写了“3组8次/4组9次”，所以该规则在这次 trace 里**不明显**（parsed 与 postprocessed 的 reps 多数一致）。但在“只写 5RM 没写次数”的输入里，这一步非常关键。

**F3. 周内 dayOfWeek 纠偏 + 补齐到 7 天（自然日占位）**

你强调过：“D1/D2/D3 是训练日标记，但系统 dayIndex/dayOfWeek 要按**自然日**占位”。阶段 2 通过 `normalizeWeekDays()` 保障这一点：

- 若模型给的 `dayOfWeek` 重复/缺失：按出现顺序分配下一个可用 `dayOfWeek`
- 一周必须补齐到 7 天：缺口用 `type:"rest"` 填充（保证自然日连续）

代码位置：`src/app/api/plan-lib/parse-template/route.ts` 的 `normalizeWeekDays()`。

你这次 trace 里（`stage2.week-1.postprocessed.json`）能看到 week=1 的 `dayOfWeek` 最终是 1..7：

- dayOfWeek=2 是 rest（把“拉伸/冷热交替洗澡…”写进 dayNote）
- dayOfWeek=4 是 rest（“休息1天”）
- dayOfWeek=6、7 是 rest（“休息2天”——模型表达的是“连续休息两天”，后处理会把它落到两个自然日里）

#### Step G：`stage2.merged.json`（按周合并后的最终模板）

含义：把所有 `week-#` 的 postprocessed 结果按周序拼起来，并计算最终 `weeks`（取最大周序号）。

这就是阶段 2 的“最终产物”，也是前端预览/导入用的那份结构。

### 2.6 留痕文件命名说明（开发/测试口径）

> 文件名目前采用英文前缀是为了“稳定 + 方便脚本处理”。但在阅读口径上，请按下表理解：

- **`stage1.*`**：阶段 1（动作识别 / parse-actions）
- **`stage2.*`**：阶段 2（计划结构识别 / parse-template）
- **`week-1` / `week-2`**：阶段 2 按周拆分调用模型的中间产物（最终会合并为 `stage2.merged.json`）
- **`raw` / `parsed` / `postprocessed`**：
  - `raw`：模型原始输出
  - `parsed`：能解析成 JSON 的版本（不代表业务正确）
  - `postprocessed`：确定性规则修正后的“业务最终版本”
