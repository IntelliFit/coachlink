## 3. 与动作库共建生态的联动（智能导入需要变化吗？）

对应 roadmap：`docs/work/roadmap/features/ecosystem/动作库计划共建生态-20260127.md`

### 3.1 结论（短答案）

**需要变化，而且主要变化在“动作匹配/复用策略”与“token 成本控制”上**，而不是模板结构本身。
+
同时明确一个产品/工程决策（与你当前计划一致）：
+
> **智能导入的自动匹配范围 = 用户私有动作库**（coach_actions / student_actions）。  
> **公共动作库不参与自动匹配**（避免规模带来的成本与误匹配）。

有公共动作库后，如果仍沿用当前做法（把“全部动作列表”塞进 Prompt），会同时产生：

- **成本不可控**：公共库一大，Prompt 体积爆炸。
- **重复动作更多**：用户本来可以“一键加入公共动作”，却被导入流程新建成私有重复动作。
- **去重/合并压力增大**：同一个公共动作可能在不同用户库里出现 N 份“同名但不同 id”的复制品。

### 3.2 当前系统已经具备的铺垫

代码里已有 canonical 关联接口：

- `POST /api/action-lib/link-canonical`
  - 代码：`src/app/api/action-lib/link-canonical/route.ts`
  - 作用：把 `coach_actions` / `student_actions` 的 `canonical_action_id` 关联到 `canonical_actions`

这说明“个人动作 → 公共动作”存在 **canonical 维度**，智能导入可以利用它避免重复创建。

### 3.3 推荐的“导入期动作复用”策略（P0/P1）

#### P0（生态阶段 1 上线后，必须做）

**目标**：导入时**只**复用“我的动作库”，未命中才新建私有动作；公共库只提供“旁路治理能力”（不进入自动匹配）。

建议把阶段 1 的输出（或 UI 表达）明确成两层：

- **自动匹配（强约束）**：
  1. 我的动作库（coach_actions / student_actions）
  2. 未命中 → 新建私有动作
- **公共库旁路（可选，不参与自动匹配）**：
  - 不参与动作匹配 公共动作库梳理太多

#### P1（为了稳定和成本，强烈建议）

**阶段 1 Prompt 不再携带完整动作库**（尤其公共库出现后）。

更稳的方案是拆解为两段确定性流程：

1. **LLM 只做动作名提取**（不带动作库上下文）
2. **服务端做匹配**：
   - 基于规范化名称/别名索引、Dice/编辑距离、子串等确定性算法
   - 返回“我的动作候选”（不返回公共动作候选，符合“不匹配公共库”的约束）

收益：

- token 成本下降（不再把动作库塞进 Prompt）
- 匹配结果更可控（可测试、可回归）
- 公共库规模增长不会拖垮导入

### 3.4 “一键加入公共动作”与导入的关系（产品层）

导入流程不做公共库搜索，但公共库仍然影响导入“质量”：

- **推荐用户先在公共动作库里“一键加入”需要的动作**  
  这样导入时会在“私有动作库”内自然命中（且可携带 `canonical_action_id`），同时减少重复动作。
- **在动作编辑/治理层做关联**  
  `POST /api/action-lib/link-canonical` 可把私有动作关联到公共动作，用于长期治理与推荐信号（不要求导入期完成）。

### 3.5 对“动作去重/合并”的影响

你们已经实现了“合并/去重”与“引用替换”。有公共库后，应补充两条原则：

- **优先把重复私有动作合并到带 `canonical_action_id` 的那一个**（长期治理更容易）
- **禁止直接删除仍被模板引用的动作**（你们已做 409 拦截），公共库上线后更重要【非要删除的话  可以提供替换动作 要不然禁止删除】

### 3.6 与计划生态（阶段 2）的关系

Roadmap 阶段 2 才做“计划生态”。智能导入在阶段 1 不必改变模板结构；
但应保证导入产物：

- 动作**允许**带上 canonical 链接（间接支持未来“跨用户复用/推荐”），但不把公共库搜索塞进导入链路
- 解析可回归（有足够测试用例与稳定的确定性规则）
