## 07. 提示词设计：动作识别与属性抽取

> 目标：把“动作识别 + 属性解析”的可控性做高，减少 LLM 猜测；让提示词能稳定地把**动作名**与**组数/次数/距离/配速/时长**拆开，并为后续结构化做准备。

### 7.1 先统一口径（避免提示词越写越散）

当前导入是两阶段：

- **阶段 1（parse-actions）**：只做动作识别与动作配置（动作名干净、尽量命中私有动作库）。
- **阶段 2（parse-template）**：解析训练日结构 + 组次 + 强度 + 备注。

因此提示词的主线应是：  
**阶段 1 不猜组次/距离/配速，阶段 2 才解析结构化字段。**

### 7.2 动作类型与属性维度（用于 prompt 规则）

系统里动作类型共有 4 类：

- `STRENGTH`：力量动作
- `CARDIO`：有氧
- `DIET`：饮食
- `HABIT`：习惯

不同类型关注的属性维度不同，提示词必须明确“允许解析哪些字段”：

- **STRENGTH（力量）**：
  - 结构化字段：`sets / reps / restSeconds / intensityConfig / durationSeconds`
  - 备注字段：`note / dayNote`
- **CARDIO（有氧）**：
  - 结构化字段建议：`distance / duration / pace`
  - 备注字段：`note`（不确定就放 note，不要猜）
- **DIET（饮食）**：
  - 结构化字段建议：`content / calories / image_url`
  - 备注字段：`note`
- **HABIT（习惯）**：
  - 结构化字段建议：`target_duration`
  - 备注字段：`note`

> 注意：若后端尚未支持对应字段，应先将解析结果放入 `note` 或 `custom_data` 中做过渡，避免“提示词要求了但系统存不下”。

### 7.3 阶段 1（动作识别）提示词建议

**核心目标：动作名干净 + 尽量命中私有库 + 不夹带强度/组次/配速信息。**

建议在提示词中加入以下硬约束（可直接复制入 prompt）：

1. **只输出动作名，不输出强度/组次/配速/休息等描述。**
2. **严禁把 RM、百分比、kg、配速、公里数拼进动作名。**
3. **“A 然后 B”必须拆成两个动作。**
4. **动作名若不确定，宁可拆分为两个动作，不要强行合并。**
5. **匹配已有动作库时，只有“高度确定同义/简称/别名”才填 matchedExistingId。**

#### 7.3.1 建议的阶段 1 输出结构（保持与现有接口兼容）

```json
{
  "actions": [
    {
      "name": "动作名称",
      "matchedExistingId": "uuid 或 null",
      "needsAutoCompute": true,
      "includesBodyWeight": false,
      "attrs": ["组数", "次数", "强度", "休息时间"]
    }
  ]
}
```

#### 7.3.2 attrs 选择规则（提示词内说明）

- **力量动作（默认）**：`["组数","次数","强度","休息时间"]`
- **计时力量动作**（悬挂/支撑/静止/保持/计时等）：`["组数","持续时间","休息时间"]`
- **不确定类型**：可先按默认力量 attrs 输出，真实字段以阶段 2 为准

> 如果需要更精准区分 CARDIO/DIET/HABIT，请升级输出结构并让后端接收 type/custom_data，否则会形成“提示词正确但入库错误”。

### 7.4 阶段 2（结构解析）提示词补强建议

**重点解决你提到的“组数/次数/公里数/配速”细腻度问题。**

建议添加下面规则段（适用于 parse-template prompt）：

#### 7.4.1 结构化字段必须有“证据片段”

当模型输出 sets/reps/distance/pace/duration 时，必须来自原文明确描述：

- 若原文没有“次数”字样，则 reps 必须为 null
- 若原文没有“公里数/米数”，distance 不能猜
- 若原文没有“配速/速度”，pace 不能猜
- 若原文没有“时长/分钟/秒”，duration 不能猜

#### 7.4.2 有氧动作解析规则（建议）

- “跑步 5km 配速 5'30''” → distance=5000, pace="5'30''"
- “慢跑 30分钟” → duration=1800, distance=null, pace=null
- “间歇跑 8×400m 配速 4'30''”：
  - distance=3200（可写入 note 或 custom_data.distance）
  - 单次间歇与配速写入 note（避免结构化字段胡编）

#### 7.4.3 饮食/习惯解析规则（建议）

- “早餐：蛋白 40g + 燕麦 60g” → DIET.content
- “日饮水 2L” → HABIT.note（或 target_duration 不适用）
- “冥想 10分钟” → HABIT.target_duration=10

### 7.5 建议的 prompt 结构模板（可直接使用）

```
角色：训练计划解析助手

任务：从文本中识别动作，并输出结构化字段。  
原则：只抽取文本中明确出现的信息，禁止猜测。

硬约束：
1) 动作名必须干净，严禁把 RM/组数/配速/公里数拼进名称
2) 未明确写出的字段一律为 null
3) “A 然后 B”必须拆为两个动作
4) 非动作内容不要输出为动作（休息日/组休/说明/测试等）

输出 JSON 结构：（略）
```

### 7.6 工程协作建议（提示词层面的配合点）

- **先写“规则 + 例子”再写“输出格式”**：模型更稳定。
- **为“模糊场景”准备兜底话术**（放 note，不做结构化字段）。
- **将关键失败样例加入 cases**：用 `stage1.prompt.txt / stage2.prompt.txt` 迭代。
