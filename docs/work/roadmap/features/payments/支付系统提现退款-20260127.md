# [需求] 支付系统补全：教练提现 + 学员退款

## 1. 文档概述

- **文档版本**：V1.0
- **创建时间**：2026-01-27
- **文档目的**：补全 CoachLink 的"资金闭环"能力，支持教练侧提现与学员侧退款（不要求一次性自动化到位，允许先手动审核/线下打款，但流程、状态与权限必须清晰可落地）。

> 说明：本需求先不展开数据库设计，只定义业务口径、页面交互、接口边界与验收标准。

---

## 2. 业务背景与价值

### 2.1 背景

- 当前系统已有"学员购买/订阅付费"的能力，但缺少：
  - **教练侧资金结算**（把平台可结算的收入提到教练账户）
  - **学员侧退款**（取消/争议/误购等场景的规范处理）
- 没有清晰流程会导致：
  - 财务对账困难、投诉处理不可控
  - 教练无法建立信任（"平台能提现吗？"）
  - 学员转化率下降（担心踩坑/不敢付费）

### 2.2 目标

- **G1**：学员可发起退款，状态可追踪，平台可审核处理。
- **G2**：教练可发起提现申请，平台可审核并执行打款。
- **G3**：所有关键动作可审计（谁、何时、对哪笔订单/哪次订阅）。
- **G4**：先支持"手动打款 + 状态流转"，后续可再接支付渠道自动化。

### 2.3 非目标（V1）

- **不做**：自动对账系统、复杂分账、多币种、税务开票、自动打款。
- **不做**：争议仲裁、证据链存证等复杂风控。

---

## 3. 角色与权限

- **学员（Student）**：仅可对"自己的订单/订阅"发起退款/撤销退款申请（在审核前）。
- **教练（Coach）**：仅可对"自己的可结算余额"发起提现申请、查看历史。
- **管理员/运营（Admin）**：可查看所有退款/提现，执行审核与打款/退款处理。
- **系统（System）**：发送通知、写审计日志、生成对账导出（可选）。

---

## 4. 核心用户故事

### US-01 学员发起退款

- **作为一个【学员】**
- **我想要【在订单/订阅详情里点击"申请退款"，填写原因并提交】**
- **以便于【我能在可控时间内拿回款项或获得明确处理结果】**

### US-02 运营审核退款

- **作为一个【运营/管理员】**
- **我想要【查看退款申请列表，按规则通过/拒绝，并记录处理备注】**
- **以便于【能标准化处理投诉/误购，减少扯皮】**

### US-03 教练发起提现

- **作为一个【教练】**
- **我想要【查看可提现金额并提交提现申请，选择到账方式并确认】**
- **以便于【我能稳定收到平台结算款，提高留存】**

### US-04 运营处理提现

- **作为一个【运营/管理员】**
- **我想要【审核提现申请并标记"已打款/失败"，可上传凭证或备注】**
- **以便于【保证资金安全与可追溯】**

## 5. 业务口径（关键规则）

### 5.1 订单/订阅与退款

- **可退款对象**：
  - 单次购买订单（如有）
  - 订阅订单（例如月/季/年）
- **退款类型**：
  - **全额退款**：未使用/短时间误购
  - **部分退款（可选）**：已发生部分权益消耗（如 credits 已消耗）
- **退款窗口**（可配置）：
  - 例如：支付后 \(X\) 小时内可"无条件全额退款"
  - 超过窗口进入"人工审核"
- **不可退款场景**（示例，可配置）：
  - 明确已使用核心权益（如已消耗大量 credits、已交付服务且完成）
  - 订单已处于"退款中/已退款"
  - 订单关联的违规/风控冻结（如存在异常支付）

> 注意：具体"已使用"判定口径，V1 可先做保守策略（仅允许未使用或极少使用），减少争议与开发复杂度。

### 5.2 教练结算与提现

- **可提现余额**的口径（V1 建议）：
  - 平台对教练的"可结算收入"，扣除退款/争议冻结部分。
  - 允许先由运营侧"手动录入/调整余额"（V1 过渡）。
- **提现方式**（V1）：
  - 支持填写：支付宝账号 / 微信收款码（图片）/ 银行卡（选一）
  - 提现申请提交后，进入审核队列
- **提现限制**（可配置）：
  - 最低提现金额（例如 100 元）
  - 每日/每周提现次数
  - 账户信息未完善不允许提现

## 6. 功能需求列表（Feature List）

### 6.1 学员端：退款申请（P0）

#### 6.1.1 入口与展示

- **入口 A**：`/me/membership` 或订单列表页的订单详情
- **入口 B（可选）**：支付成功页提供"遇到问题？"入口
- 订单详情需展示：
  - 订单金额、支付时间、商品/订阅名称
  - 已使用情况摘要（如 credits 消耗概览）
  - 退款状态（未申请/审核中/已退款/已拒绝）

#### 6.1.2 退款申请表单

- 字段：
  - 退款原因（枚举 + "其他"文本）
  - 备注（可选）
  - 证据图片（可选，最多 3 张）
- 校验：
  - 同一订单同一时间只能存在一个"进行中"的退款申请
  - 在"审核前"允许撤销申请（变为已取消）

#### 6.1.3 状态流转（退款）

- `draft`（填写中，可选） → `submitted`（已提交） → `approved`（已通过） → `refunded`（已退款）
- 或：`submitted` → `rejected`（已拒绝）
- 或：`submitted` → `cancelled`（已撤销）

> V1 建议至少实现：`submitted / approved / rejected / refunded / cancelled`。

### 6.2 教练端：提现申请（P0）

#### 6.2.1 入口与余额

- 入口：教练后台（Dashboard）新增「提现/结算」页
- 展示：
  - 可提现余额
  - 结算中（冻结/审核中）的金额
  - 历史提现记录（列表）

#### 6.2.2 提现申请表单

- 字段：
  - 提现金额（<= 可提现余额）
  - 到账方式（支付宝/微信/银行卡）
  - 收款信息（账号/收款码/银行卡信息）
  - 备注（可选）
- 校验：
  - 余额不足提示
  - 未完成身份/收款信息配置提示
  - 最低金额/频率限制提示

#### 6.2.3 状态流转（提现）

- `submitted`（已提交） → `approved`（已通过） → `paid`（已打款）
- 或：`submitted` → `rejected`（已拒绝）
- 或：`approved` → `pay_failed`（打款失败，可重试）
- 允许运营侧"撤回/作废"（仅在未打款前）

### 6.3 管理后台：退款/提现处理台（P0）

#### 6.3.1 列表与筛选

- 退款列表：
  - 按状态、时间、学员、订单号筛选
- 提现列表：
  - 按状态、时间、教练、金额区间筛选

#### 6.3.2 审核与处理动作

- 退款：
  - 通过/拒绝
  - 备注必填（拒绝原因）
  - 标记"已退款"（V1 可由运营手动确认外部退款完成）
- 提现：
  - 通过/拒绝
  - 标记"已打款/失败"
  - 可上传打款凭证（截图/转账单号）

#### 6.3.3 审计日志（P0）

- 任何状态变更必须记录：
  - 操作人（adminId/role）
  - 操作时间
  - 变更前后状态
  - 备注/原因

## 7. 通知与触达（P1）

- 学员：
  - 退款申请提交/通过/拒绝/退款完成 → 站内通知 +（可选）Web Push
- 教练：
  - 提现申请提交/通过/拒绝/打款完成/失败 → 站内通知 +（可选）Web Push

## 8. 非功能需求

- **安全**：
  - 退款/提现接口必须校验用户身份与资源归属
  - 防重复提交（幂等）
- **可用性**：
  - 管理台操作要有二次确认
  - 所有错误要返回可理解提示（不要只报 500）
- **可观测**（可选）：
  - 退款/提现转化漏斗：提交量、通过率、平均处理时长

---

## 9. 验收标准（Acceptance Criteria）

### 9.1 学员退款

- 学员能在订单详情发起退款，提交后在列表/详情看到状态为"审核中"
- 运营在管理后台可看到该申请，并能通过/拒绝，学员侧状态同步更新
- 同一订单不能重复发起多个进行中的退款申请
- 学员在"审核前"可以撤销申请

### 9.2 教练提现

- 教练能看到余额与历史记录，并提交提现申请
- 运营可审核并标记"已打款/失败"，教练侧可见
- 余额校验与最低金额校验有效

### 9.3 审计

- 任意状态变更均能追溯（至少在管理台可查看日志/备注）

---

## 10. 边界情况 / 异常处理

- 学员申请退款时，订单已处于退款流程中 → 提示并禁止提交
- 运营已通过退款但实际退款失败（支付渠道原因） → 允许标记失败并触发重试流程（P1）
- 教练提现申请通过后，教练修改收款信息 → 不影响已审核单；新申请使用新信息
- 运营误操作（通过/拒绝） → 需要"更正流程"（P1，可通过创建补偿记录解决）
