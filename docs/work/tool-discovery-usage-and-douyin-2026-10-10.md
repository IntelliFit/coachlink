# 工具入口、模块使用统计与抖音小程序评估

日期：2026-10-10（Asia/Tokyo）。本轮完成源码核对、真实数据库只读聚合及抖音官方文档研究；没有业务代码修改、构建、测试、提交、上传或部署。下述布局与抖音首版范围为建议，不视为用户已确认实施方案。

## 结论

单杠地图有实际贡献使用，力量计算器已有明显的小程序保存使用；目前缺少小程序页面访问、游客和本地计算事件，不能判定单杠地图是全模块使用第一，也不能用上传人数推算浏览人数。优先改善这两个入口有依据，同时必须补采集才能观察效果。

抖音端技术上有复用基础，但当前包不是可直接发布的抖音小程序。地图能力与视频挂载存在类目及账号条件；先确认权限，再做原生轻量工具版。不能把已有 `build:tt` 命令解释为已支持上线，也不能承诺取得流量。

1. 普通入口 `pages/index/index` 加载今日训练；学生底栏是训练、教练、知识、工具箱、我的。

3. 教练身份底栏没有工具箱。入口调整须同时考虑游客、学员、教练三种身份。
4. 地点分享已有 `/streetlifting/index/location-share?locationId=…` 专用落地页，通用地图列表已有 `/streetlifting/index/locations`。推广工具可以复用直接落地能力，不必全部先经过训练首页。
5. 本轮未识别到 9400–9499 范围内可复用自动化监听，也未取得可识别的开发者工具主窗口；没有新开窗口、导航、切登录态或制造截图。因此本轮属于源码与数据研究，不是完成了截图设计审查或真机体验验收。

## 微信入口建议

- 统一对外名称为“单杠地图”，副说明“找附近单杠、看照片、去训练”；继续保留双杠、云梯等器材筛选。
- 工具箱顶部用“快捷工具”，固定单杠地图、力量计算器；第三个位置优先展示最近使用，暂无真实热度时不标榜“最热门”。完整工具列表保留，暂未开放工具降到后面。
- 有计划用户：首页主要训练卡仍优先可见，在卡下放紧凑快捷入口；不占用周历、训练处方或开始训练的位置。无计划/游客首页让找单杠和计算器更容易看到。教练视角也应有工具入口。
- 推广某个工具时，小程序码、分享卡直接落到该工具；分享某个地点继续落到地点详情。文案写清功能名，不要求用户记住内部模块路径。
- 保持公共浏览与计算可用；保存、上传、贡献等写操作才提示登录。不能为了统计而给地图浏览增加登录门槛。
- 使用现有纯色品牌按钮 `#CF6D4E` 和 8rpx 栅格；新增最近使用缓存复用公共缓存约定，最长 60 天，云端权威数据规则不变。

实施后需要实际小程序截图与入口导航验收；本轮没有 UI 改动，不提前宣称布局已通过。

## 统一模块统计的首版口径

决策问题是“推广是否能让用户找到工具、获得结果并回来使用”。每个模块先统一三类主指标，不用事件数量单独决定优先级：

| 指标 | 定义 | 用途及限制 |
|---|---|---|
| 模块访问 UV | 正式环境内，模块进入事件的去重 actor | 反映被发现程度；游客用匿名设备身份，账号可做登录后连接，但不能称为跨设备真实人数 |
| 有效使用 UV / 使用率 | 完成模块价值动作的 actor；除以访问 actor | 地图看地点详情、计算器得到有效结果、视频分析完成等分别定义；导航只表示发起/接口成功，不证明到达 |
| 7 日内再次使用率 | 首次有效使用后第 1–7 天又有效使用的 actor / 已有完整 7 天观察窗的首次使用 actor | 反映重复价值；近期未满 7 天的 cohort 不进入分母 |

诊断辅助只保留：快捷入口曝光→点击→模块进入转化，及推广来源→直接落地→有效使用漏斗。7/30 日窗口、角色、微信/网页/抖音、正式/体验/开发版本分开显示。改入口前后比较相同渠道、新老用户及完整窗口；没有足够基线时不杜撰提升目标。

建议事件最小集合：`module_enter`、`shortcut_exposure`、`shortcut_click`、`module_action_success`。动作枚举再区分地图详情/导航发起/贡献成功、计算结果/保存成功、游戏开局/完成、视频任务提交/分析完成、知识阅读和训练关键操作。所有重试事件带稳定 event_id，服务端幂等；页面 show 防重复，批量非阻塞上报，失败不弹业务 toast、不阻塞导航；离线队列有条数与有效期上限。

事件字段限定 module_id、action、source、campaign_id、scene、surface、env_version、build_version、session_id、anon_id、发生时间及 event_id。登录身份从服务端令牌取得，不能相信客户端提交的 user_id；现有 behavior 接口要求登录，不能原样复用于游客统计。开发/验收/机器人流量排除，后台查询限管理员；不上报经纬度、手机号、训练正文或视频内容，按现有隐私告知约束采集。

现有统计页可扩展，但需先修正采集覆盖与全量分页/聚合口径；不能只给空视图加一个图表。历史缺失访问无法凭新埋点补造。微信后台页面分析可作为另一来源，仍需实际账号授权和导出，不将其假装已查询。

## 抖音技术与准入评估

### 现有复用条件

`apps/wechat/package.json` 已有 `build:tt` 及 `@tarojs/plugin-platform-tt@4.1.11`。可复用地图点位 API、器材标签、坐标与筛选规则、计算规则及部分 React/Taro UI。仍需平台适配：

- 微信登录目前向 `/api/miniapp/wechat-login` 交换 code；抖音须独立 code 交换及账号绑定机制，不能把 tt code 发给微信登录接口。
- 定位、选点、打开地图、地图组件及坐标需逐项验收。现有 WGS84/GCJ02 标记必须保留，不能批量改写历史坐标；抖音 openLocation 接受 gcj02。
- 分享、头像/手机号授权、隐私告知、环境识别、相册和媒体接口需平台隔离；第一版若只读工具可减少登录与媒体迁移成本。
- 现有 config 的 outputRoot 默认仍跟随微信 dist/dist-release；抖音必须独立固定输出，不能直接运行现有命令覆盖正在使用的微信包。若建立客户端，放在 `apps/` 下，与根 monorepo 统一管理，不在根目录新建 app/。
- 训练/教练/会员/支付迁移不属于“一键编译”的范围。未做 tt 构建或真机试运行，不能给出精确复用比例、工期或包可发布结论。

### 官方文档已确认的限制

1. 视频自主挂载需单独申请、审核及绑定账号；小程序上架不等于可挂载。企业主体需要符合规范的同主体抖音企业机构账号；个人主体普通账号另有实名、有效粉丝等条件。用户实际账号主体、类目及可申请能力尚未核对。
2. 2024-04-23 后注册的小程序，getLocation/openLocation/chooseLocation 是申请能力，主营类目须符合开放条件。公开文档正文未提供完整可解析类目表，本轮不能确认“户外单杠查询”一定可申请；先在控制台或官方工单核实三个权限的实际条件。
3. 自主挂载要求原生页面和完整有用的功能，不宜只把 Web 站套 webview，也不能仅以跳转外部平台作为落地价值。地图浏览、器材筛选、地点详情及计算结果应形成在抖音内可用的工具体验；官方亦会评价功能简单程度，增加几个工具不等于保证过审。
4. 若地理权限不通过，可先保留手动选城市/搜索、点位照片地址等可行阅读能力；地图展示本身仍需确认组件可用，不把降级版本宣传为已支持实时附近定位、选点或导航。

建议推进顺序：微信入口与采集方案 → 核实抖音主体/主营类目/地图权限/挂载资格 → 原生地图与计算器试点 → 按有效使用与复访数据决定是否扩大至完整训练平台。推广落地应优先展示视频里提到的地点或工具。
