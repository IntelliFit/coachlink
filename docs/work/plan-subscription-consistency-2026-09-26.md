# 计划推进、训练历史与订阅权益：一致性整改方案

日期：2026-09-26。状态：诊断与实施建议，**尚未实施本方案或修改生产数据**。本文不是新的已批准计费规则。

## 1. 结论与证据

问题不是一个日期公式算错，而是可修改的训练记录同时承担历史事实、计划推进和订阅生命周期输入，且客户端各自计算排期。补组、重试或重新选中 attempt 后，其他结果会跟着变化。

本轮已完成：相关代码、既有业务决策、CI 与测试审计；7 个相关测试文件共 37 项全部通过；另用现有纯函数复现“只修改历史完成时间，推荐进度从 D7 退回 D3”。没有修改已有测试或业务代码，没有写生产数据库。

| 发现 | 证据 | 结论边界 |
| --- | --- | --- |
| 补历史组会改首次完成时间 | `src/app/api/execution/complete-set/route.ts`、`complete-item/route.ts` 在再次满足自动完成条件时写入当前时间；该学员 D53/D57 的生产数据和请求日志吻合 | `/finish` 本地幂等修复不能覆盖另外两个写入口 |
| 历史修改可以回退推进 | `src/lib/planProgress.ts` 用完成时间串联恢复日的生效时间；见下面最小反例 | 不只是日历颜色问题，也不是加一个日期排序能解决 |
| Web 与小程序排期不一致 | 同一学员 9/26 数据下 Web 显示 D55，小程序显示 D68 | 当前画面不等于统一业务状态；不能挑较大的数作为正确答案 |
| 当前额度和跨计划结转使用不同单位 | `subscriptionCredits.ts` 按去重已完成训练日；`subscriptionCarryover.ts` 按已完成记录涉及的周跨度及迁移起点折算周数 | 部分周换计划、训练频率变化需要明确换算规则；尚不能断言每个订阅都已扣错 |
| 查询失败可能被当成“没有消耗” | `getSubscriptionCarryoverSummariesBatch` 在实例查询失败时返回初始化的完整剩余周数；execution 查询也未区分错误 | 是静态代码风险，尚未证明该学员经历过这一错误 |
| 现有绿灯不能挡住回归 | `.github/workflows/test.yml` 的单测有 `npm test || true`，E2E 有 `continue-on-error: true`，触发分支缺少实际使用的 `dev` | 其他步骤仍可能让任务失败，但测试失败本身被放行 |
| 规则文档互相冲突 | 旧“自洽规范 v1”仍标“已拍板”，要求 maxCompleted 推进和未开始不展示日期；较新的 `DECISIONS.md` 已规定严格顺序、恢复日和未来排期 | 实施前必须归并有效规则，并把旧规范明确标为历史，而不是继续并列维护 |

历史自然日期上的 Day 可以因真实补练而不按数字排序；不能仅凭 D60 后显示 D53 就认定训练事实非法。此次已证实的问题是**补录改写时间，并使推进、今日卡片与历史权限发生连带变化**。

### 最小反例：现有单测通过，但业务不变量失守

固定北京时间 2026-09-26：D1、D4、D7 为训练日，其他为纯恢复日。D1 在 9/10 完成，D4 在 9/14 完成，严格推进函数推荐 D7。仅把 D1 的 `completed_at` 改到 9/25，推荐变成 D3；其他状态完全没改。

可在仓库 PowerShell 中运行，纯内存计算，不访问数据库：

```powershell
@'
const { deriveStrictSequentialProgressDay } = require('./src/lib/planProgress.ts');
const planDays = Array.from({ length: 7 }, (_, i) => ({
  dayIndex: i + 1, type: [1, 4, 7].includes(i + 1) ? 'training' : 'rest'
}));
const original = {
  1: { status: 'completed', completed_at: '2026-09-10T08:00:00Z' },
  4: { status: 'completed', completed_at: '2026-09-14T08:00:00Z' }
};
const corrected = {
  ...original, 1: { ...original[1], completed_at: '2026-09-25T08:00:00Z' }
};
const calculate = executionsByDayIndex => deriveStrictSequentialProgressDay({
  planDays, startExecutionDay: 1, executionsByDayIndex,
  explicitStartDate: '2026-09-10', today: new Date('2026-09-26T04:00:00Z')
});
console.log(JSON.stringify({ before: calculate(original), after: calculate(corrected) }, null, 2));
'@ | node --require tsx/cjs
```

这个反例用于证明风险，不表示正确修复是允许任意修改完成时间后仍强制取历史最大指针。真正需要保护的是历史事实和已确认的推进事件。

## 2. 先明确四个独立问题

| 对象 | 回答的问题 | 不应承担的职责 |
| --- | --- | --- |
| 训练记录 / attempt | 哪次训练做了什么、何时实际训练、何时保存和确认 | 不能因一次空重试抹掉其他记录或重置订阅 |
| 计划日状态 / resolution | Dn 是否已完成、明确跳过或结束恢复；接下来允许做什么 | 不能由当前选中的日历格或最后编辑时间决定 |
| 日历 | 历史事实放在哪一天，未来如何预计安排 | 不能独立决定扣费、推进或历史访问权限 |
| 订阅权益 | 获得多少服务额度、消耗多少、剩余多少、能否继续服务 | 不能直接把自然日过去多少等同于权益耗尽 |

保留现有 B1 已确认原则：购买周数不是自然日硬到期；计划总长度、权益可执行范围、前端预览窗口分开；新阶段计划从自己的 D1 开始，余额限制可执行量，不把起点强行挪到计划尾段。

严格顺序与纯恢复日规则仍遵循 7 月决策：未解决训练日不能跨过；纯恢复日自然跨日或用户主动进入其后的首个训练日才推进。浏览后续日期不推进。5 小时超时不自动视为完成。

### 首批固定不变量

1. 修改已完成训练的重量、次数、备注等内容，不改变首次完成事实、不重扣权益、不使推进回退。
2. 一个逻辑训练日可有多次 attempt，但计费完成最多一次；结束空 attempt 不等于主动跳过训练日。
3. 同一完成命令重试任意次，结果等价于执行一次；服务端提交后客户端丢失响应也适用。
4. 已完成历史不受“未来预览周数”限制；仍须校验本人或有权教练，不能绕过身份权限。
5. 同一天可展示多个 Day；不能后写覆盖。查看历史不创建新的空训练。
6. 同一事实快照、规则版本、北京时间与 now 输入，所有端输出相同业务结果。
7. 请求失败是“暂时未知”，不是“没有计划”“剩余额度全部恢复”或“训练清零”。
8. 更新计划保留实例 ID 和历史关联；正在执行的训练仍使用启动时快照。
9. 常规补录与重试不回退进度；真正撤销完成、纠正迁移起点等特殊操作必须显式、可审计，不能用 `max(oldPointer, newPointer)` 隐藏错误。

## 3. 代码怎么收口

### 3.1 保护时间语义，所有完成入口统一

- 区分 `plannedDate`（预计排期）、`performedOn`（实际训练归属日）、`firstCompletedAt`（首次确认完成事件时间）、`updatedAt`（最近编辑时间）。字段名为建议，不是已完成迁移。
- 首次完成时间一经确立不能被普通补组覆盖；补录、纠错使用独立审计记录。实际训练日期未知时保留未知，不能默默用今天、开始时间或访问日志猜测。
- 老字段兼容期间，完成写入也必须只在首次状态转换时赋值。`finish`、`complete-set`、`complete-item`、超时补记全部调用同一个完成事务。
- 明确区分“更新已完成记录内容”“确认超时记录完成”“重新训练”“主动跳过”，不用同一个通用保存接口隐式猜意图。
- 状态转换、计划日确认及相关权益记账同一事务提交；锁 plan instance / execution 或使用版本条件更新，避免并发保存 JSON 组数据丢失。
- 通知、统计等事务外工作通过可重放的幂等任务处理。数据库唯一约束负责最后一道防重，不只靠按钮防抖。

### 3.2 服务端提供统一状态快照，客户端不各算一遍

- 复用现有 `@coachlink/core` 承载无网络、无隐式系统时钟的领域函数；保留并归并现有 credits / entitlement 模块，不推倒重写所有订阅逻辑。
- 服务端聚合返回 `policyVersion`、`stateVersion`、`asOf`、下一次时间失效点、推进状态、历史事件桶、未来排期、权益以及权限和原因码。读取应基于一致版本，避免混入更新前的额度和更新后的训练。
- 日历用 `dateKey -> events[]`；今日卡片、周视图、月历、教练端读取同一结果。App 同步契约，旧客户端由 API 适配兼容。
- 权限拆成“可查看历史 / 可预览 / 可开始 / 可继续 / 可补记”，不能只有一个 `disabled`。
- 把逻辑日已确认状态与某个“当前 attempt”分开保存或归纳；选择展示哪次记录，不得改变该逻辑日是否已经确认完成。
- 客户端保留账号隔离的 60 天缓存，明确区分本地待同步与云端已确认数据。云端为准，但旧响应版本不能覆盖新响应；跨午夜需刷新时间相关派生状态，不能只看写入版本。

### 3.3 订阅建立可核对的权益流水，不顺手改变商业规则

- 发放、消耗、撤销、结转、人工调整都能追溯来源；训练消耗使用“订阅 + 稳定逻辑训练日身份”的唯一业务键，不能按请求次数或 attempt 数计费。
- 购买与阶段分配保留规则版本/训练频率快照；教练调整未来训练日数量不能静默改写历史已发放额度。
- “周”如何折为“训练次数”、只练半周后换计划、每周 2 次改为 4 次、赠送 `no_charge` 阶段，必须有明确算例。现有代码口径不一，不能让技术改造擅自替用户决定余额。
- 新流水先按既有已确认规则试算，与原结果逐项对账；有歧义的余额列为待核对，不自动补发、扣减或归零。
- 订阅权益、服务关系和预计完成日分别输出；继续训练的权限不能直接取一个可能过期的预计日期。

## 4. 怎么测试：测连续行为和精确结果

每个用例断言同一组结果：逻辑推进日、实际归属日、首次完成时间、已用/剩余额度、历史事件集合和访问权限。只断言 HTTP 200、页面有“剩余天数”或没有报错，不足以验收。

| 必测场景 | 精确验收重点 |
| --- | --- |
| 完成 → 跨两周 → 回看补组 | 历史仍在原归属日，首次完成不变，推进不退，消耗不增 |
| 同次完成请求重发 10 次；成功后断网再重试 | 同一完成事件、同一扣减，无重复 attempt 或关联任务 |
| 两台设备同时保存不同组；最后一组与 finish 并发 | 不丢组、不覆盖新值、完成只发生一次；冲突须明确返回 |
| 超过 5 小时 → 有内容旧记录 + 较新空记录 → 恢复/补记/重练 | 原内容可恢复；超时不推进；补记不伪造缺失组；重练保留原 attempt |
| 北京时间午夜、5 小时前后、权益耗尽后的宽限边界 | 使用固定虚拟时钟断言边界两侧，不依赖测试机器当前日期 |
| 连续恢复日 → 只预览后续训练 → 真正开始后续训练 | 预览不推进/压缩，真实开始按已批准恢复日规则执行 |
| 同日两个训练日、长期顺延、完成计划最后一天 | 多事件不互相覆盖；未来排期不留洞；结束不误回 D1 可开练 |
| 补历史 D53/D57，已有较后 D60/D64/D67 | 用脱敏事实重放，内容编辑不能重新制造倒退；历史不被未来周锁挡住 |
| 计划修订时已有进行中训练 | 实例 ID 和历史关联不变；旧 execution 快照不变，后续使用新版本 |
| 部分周换阶段、不同频率、赠送阶段、续费/重复发放通知 | 按明确算例核对余额，不重复发放或消耗，不用周跨度代替未经确认的结转规则 |
| 多教练、多订阅、不同账号 | 记录、缓存、权益完全隔离；越权读写失败，不泄漏数据 |
| 请求失败、乱序响应、刷新、退出重登、旧客户端 | 有效历史不消失，旧版本不覆盖新版本；服务端仍守住写入规则 |

分层实施：

1. **领域单测**：手工算例作为独立预期；先加入能复现此次问题的失败用例，再修复。共享包测试要纳入 Vitest，当前 include 只有 `src` 和 `tests`，不会自动覆盖 `packages/core`。
2. **长序列测试**：用虚拟时钟走完 84 天，不需要真的等三个月。组合开始、保存、断网重试、超时、补录、跨日、修订、续费，逐步检查不变量；再做固定种子的随机序列，建议夜间 500 组 × 100 步起步，保存种子并缩减成最小失败案例。
3. **真实数据库集成测试**：隔离 PostgreSQL 执行真实事务/RPC，验证并发、唯一约束、回滚和“提交成功但响应丢失”；不能仅 Mock 掉数据库后声称事务已可靠。
4. **跨端契约 + 定向 UI**：同一快照对比 Web/小程序/App 的业务数据；实际验证补录、历史回看和今日卡片。保留登录、刷新会话、计划 CRUD 三类既有门禁与可执行 AI 回归 Prompt；补上训练长链路，不靠口头测试说明。
5. **验证测试本身**：有意恢复“补组覆盖 completed_at”或重复扣减的错误实现时，相关测试必须失败。旧代码不是新引擎的正确性标准，只能作为差异比较对象。

所有写测试只用隔离环境/专用测试数据，记录主键并在 `finally` 清理，随后查询验证没有残留；清理失败也必须使测试失败。真实学员账号仅做获授权的只读核查，不用于练习完成、跳过或续费。

## 5. 发布与后续保障

- CI 覆盖实际 `dev` 和发布分支；去掉测试失败放行，用 `if: always()` 单独上传报告。不要为了生成报告把失败改成成功。
- 合并/发布需要测试门禁真正通过；修改推进、订阅、执行 API 时必跑对应集成和定向 E2E，普通无关改动不用每次跑全部 UI。
- 发布产物绑定通过测试的 commit、镜像摘要和迁移版本；本地测试通过不等于生产已部署。小程序旧版本并存时，后端仍保证不变量。
- 数据迁移先新增兼容字段，再上线兼容写入，最后切换读取。新旧模型对同一只读快照、同一 now 进行影子比对，差异逐项分类为预期修复/新错误/历史歧义。
- 先小范围试运行，核对历史可访问、推进和权益再扩大。回滚代码不能自动撤销已产生的账目；数据修正使用明确调整记录，不能删历史掩盖差异。
- 加入“历史完成时间被普通编辑改变、非显式操作导致进度倒退、重复消耗、余额异常、端间版本不一致”等检查和有上下文的告警，日志不记录训练/健康正文。本文只提出监测设计，没有创建监控任务。

## 6. 实施顺序与完成标准

| 阶段 | 边界 | 完成标准 |
| --- | --- | --- |
| A：固定规则与防止新损坏 | 整理有效规范；补复现测试；统一所有完成入口；超时恢复；拆开历史查看与未来开始权限 | 历史补录反例从失败到通过，所有完成入口的重试/并发不再改首次事实；真实案例脱敏重放通过 |
| B：统一推进和日历 | 共享领域计算 + 服务端状态快照 + 多 Day 事件桶；客户端迁移 | 同一输入三端业务结果一致；今日/周/月一致；完成记录不因解锁窗口无法查看 |
| C：订阅结转可对账 | 先明确部分周/频率变化算例，再引入版本化权益流水 | 历史余额逐项可解释，新购/续费/结转/赠送有精确断言，无未经确认的自动调账 |
| D：发布防回归 | CI 阻断、影子比对、隔离回归、分阶段发布及异常检查 | 故意引入典型错误时 CI 拦截；灰度无未解释差异；可定位、可重放、可恢复 |

不要把该学员的指针直接改到 D68，也不要按当前 `completed_at` 批量重排历史。D57 的实际训练归属存在 9/14 与 9/17 的证据歧义，应保留所有 attempt，单独确认实际日期；请求日志里的首次 finish 也不必然等于实际训练日。

首个实施单元建议限定为阶段 A 的“补录不改首次完成事实 + 完成入口幂等”，不同时修改套餐价格、支付渠道或结转商业规则。现有本地超时恢复改动尚未发布，实施时应复用并核对，而不是另建一套。

不能承诺系统永远零 bug。可以建立可验收的保障：已知故障可自动复现并被阻断、关键数据约束不能被普通接口绕过、线上异常有记录可恢复、每次新增边界案例进入永久回归。
