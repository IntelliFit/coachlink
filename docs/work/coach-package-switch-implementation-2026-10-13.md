## 实现

- 小程序：已有订阅可直接点不同套餐，显示价格、时长及接续规则；购买前验证后端接续能力，支付参数传目标 `productId`、`months`。支付响应也必须明确 `after_current`，避免旧后端忽略新参数后让用户付款。原套餐仍使用原续费入口。
- Web/App：不同套餐使用独立业务订单，保存后端核对的目标商品快照和接续标识；Web、小程序展示待生效套餐。未执行 Web/App 界面验收；本机未找到 Web 所需的 `web-devtools` skill。
- 后端：根据教练商品配置验证套餐、时长和价格；不信任客户端提供的新套餐名称、档位或履约指令。旧 Web 支付入口清除客户端注入的接续履约元数据。
- `coach_subscription_package_queue` 保存每笔商品快照、待生效权益与支付来源。来源唯一键使重复支付通知不重复发权益。表启用 RLS，表与函数仅授权 `service_role`，函数使用 `SECURITY INVOKER`。
- 同套餐续费与套餐切换共用订阅行锁；并发续费不会覆盖切换后的周数。付款延迟导致原 SKU 已不是当前套餐时，按该付款的原商品快照排队，避免延长错误服务。
- 复用现有服务周/历史执行计算判定旧权益耗尽。支付确认、订阅读取和训练结束后的日期更新可触发检查；仍有剩余权益或有进行中的训练时不切换。多个接续套餐按购买顺序生效，退款/关闭/失败的来源不激活。
- 生效时保留订阅关系 ID、历史执行、视频、反馈与订单；归档旧计划定义，更新当前商品及本笔支付信息，并建立待教练安排新套餐计划的工作项。不同服务不沿旧目标自动生成下一阶段。新权益不能用于继续旧计划写操作，原执行记录仍可查看。

主要代码：`src/lib/subscriptionPackageQueue.ts`、`src/lib/subscriptionOrders.ts`、微信/支付宝支付履约、`package-switch-preview`、订阅读取与训练访问检查；客户端为教练价格页及支付服务。

迁移：`supabase/migrations/20261013142403_coach_subscription_package_queue.sql`，由既有 CLI 创建，整个文件以事务执行。上线需先应用迁移并部署配套后端，再交付新客户端；当前未上线。
