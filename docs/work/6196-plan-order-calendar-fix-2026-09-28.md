## 原因与修复

原实现用 completed_at 锚定历史月历，因此晚点确认会把较早的 D 放到后面的训练之后；上轮仅提示核对，未修安排投影。另外订阅起始时间在北京时间跨日，D1 被过滤后推断执行起点为 D2，D1 又被起点前逻辑放回原始六月排期。

```text
教练原计划 D 顺序 + 已完成记录
        ↓
已确认训练日 / 原始完成时间（保留原值）
        ↓
安排投影：有效保存/迟补开始日期候选 → 按原D间隔向前校正倒序
        ↓
同一 core 模型 → Web 月历、周条 / 小程序月历、周条
        ↓
推算标签 + 原始提交日期可追溯（不写数据库）
```

- `packages/core/src/planCalendar.ts`：默认 recorded 用于原始记录，安排入口明确指定 plan-order。候选日期和倒序校正仅改变显示；未确认的推算加 dateEstimated。performed_on 优先于旧 completionDates。
- `src/lib/planProgress.ts`：D1 也参与最早训练记录推断。显式线下迁移起点保留。
- Web、微信小程序均使用共享投影，不各写一套排序；推算由现有派生模型计算，未新增 effect 同步状态（按 React 检查规则复核）。
- 原始 D 编号、执行 ID、训练内容、完成数量和服务周余额不变。同日真实完成多条 D 仍保留。
