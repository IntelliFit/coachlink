# 力量训练 1RM 动态管理方案 (1RM System Design Strategy)

针对学员在长周期计划中 1RM（One Repetition
Maximum）发生变化导致原计划负荷不再适用的问题，我们建议采用 **“动态锚点 +
自动调节”** 的混合策略。

## 1. 核心理念：隐式追踪与持续估算 (Continuous e1RM Estimation)

打破“必须专门测试才能更新 1RM”的限制。每一次训练都是一次潜在的测试。

**核心逻辑：** 任何一组训练数据（Weight x Reps），只要通过了有效性校验（如 RPE
足够高），都可以通过公式（如 Epley 公式）转化为一个 **估算 1RM
(e1RM)**。如果这个 e1RM 高于历史记录，系统自动识别为“进步”，并更新基准。

### 强度定义的灵活性

计划不仅支持 `% 1RM`，也天然支持 `XRM`（如 12RM）作为强度锚点。

- **12RM** 本质上就是 `~70% 1RM`。
- 系统内部统一将其从 1RM 换算为绝对重量推荐给用户。

## 2. 智能闭环流程

### A. 执行监测 (Execution Monitoring)

学员在训练中输入实际完成数据（例如：计划 70kg，实际做了 75kg x 5 reps）。

1. **触发计算**： $$ e1RM = Weight \times (1 + 0.0333 \times Reps) $$
   $$ e1RM = 75 \times (1 + 0.0333 \times 5) \approx 87.5kg $$
2. **有效性判断**：
   - 必须是正式组（非热身）。
   - 用户实际完成情况显示 RPE > 7 (或接近力竭)。

### B. 自动更新 (Auto-Update)

系统将本次计算出的 e1RM (87.5kg) 与 `personal_records_history` 中该动作当前的
1RM (假设为 80kg) 进行比对。

- **判定进步**：87.5kg > 80kg → **New PR!**
- **写入记录**：自动向 `personal_records_history` 插入一条新记录：
  - `weight`: 87.5
  - `estimated_from`: { "weight": 75, "reps": 5 }
  - `is_auto_calculated`: true

### C. 动态反馈 (Dynamic Feedback)

一旦数据库更新，后续所有基于 `% 1RM` 或 `RM` 的计划推荐重量立即改变。

- **即时性**：下个动作如果是“深蹲 80% 1RM”，推荐重量立即变为
  `87.5 * 0.8 = 70kg`（原为 64kg）。

## 3. 历史曲线与可视化

### 数据来源区分

| 表名                       | 存储内容                     | 用途                                     |
| -------------------------- | ---------------------------- | ---------------------------------------- |
| `plan_instance_executions` | **每日**所有组的实际完成数据 | 计算每日 e1RM，绘制完整波动曲线          |
| `personal_records_history` | 仅存储**突破记录 (PR)**      | 里程碑标记、成就系统、曲线上的 ⭐ 高亮点 |

### 曲线绘制逻辑

1. **数据源**：遍历 `plan_instance_executions` 中该动作的所有执行记录。
2. **每日估算**：从 `action_executions` JSONB 中提取 `weight` 和
   `reps`，使用公式计算该日的 `e1RM`。
3. **连点成线**：所有日期的 e1RM 数据点连接成曲线。
4. **PR 高亮**：`personal_records_history` 中的记录在曲线上标记为 ⭐ (突破日)。

### 曲线价值

- **完整波动**：展示学员的真实状态起伏（疲劳、恢复、突破）。
- **趋势分析**：即使单日有下降，整体趋势应上升（渐进超负荷）。
- **疲劳检测**：连续多日 e1RM 下滑可能预示过度训练，系统可提示休息。

## 4. 应对“计划失效”的机制

针对您提到的场景：“计划写了 70kg，学员状态好做了 75kg”。

- **Before**：学员做了就做了，下次计划可能还是默认按旧标准生成。
- **After**：
  1. 学员录入 75kg x 10 reps。
  2. 系统后台计算 e1RM ≈ 100kg。
  3. 系统发现旧 1RM 为 90kg，**自动更新**为 100kg。
  4. **下周计划自动调整**：原本基于 90kg 安排的 80% (72kg) 自动变为 80kg。

**结论**：计划本身不需要修改，因为计划存储的是 **逻辑 (80% 1RM)**。只要变量
(1RM) 被自动更新了，计划就永远是“新鲜”且适配的。

## 4. 总结与建议 (Summary)

**回答您的核心问题：**

1. **初始问卷**：不仅仅是参考，应直接作为第一笔数据存入
   `personal_records_history`。
2. **两个月后的变化**：
   - 依赖 **实时计算**（前端/后端渲染时计算，而非存死数据）。
   - 依赖 **过程中的更新**（测试日、AMRAP 估算、手动更新）。
3. **系统设计**：
   - 确保 `coach_plan_instances` 存储的是比例（Ratio）。
   - 确保 `personal_records_history` 是单一真实数据源（SSOT）。

通过这种方式，计划就像一个公式，而 1RM
是变量。变量变了，结果自然就变了，完美解决了长周期计划的适应性问题。
