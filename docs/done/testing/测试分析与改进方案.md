# 测试分析与改进方案（工程质量）

> 目标：把测试从“跑一跑”升级为“口径固化 + 防回归”。
>
> 本文档面向：研发负责人 / 需要制定质量标准的同学。

---

## 1. 现状痛点（典型）

- **业务口径复杂**：订阅 B1 credits、计划覆盖语义、执行进度推导等，很容易“改一处炸一片”。
- **缺少可执行规格**：很多逻辑只存在于口头/代码里，缺少“测试就是规格”的锚点。
- **E2E 成本高**：全量 E2E 慢，容易没人跑；但关键链路不测又容易线上事故。

---

## 2. 测试目标分层（建议）

### 2.1 口径固化（优先级最高）

- 把“不可争辩的口径”写进测试：
  - credits total/used 计算
  - 线下迁移扣减规则
  - nextDayIndex 推导（含 skip/abandon 的影响）

> 推荐落点：`src/lib/*` + `*.test.ts`

### 2.2 API 行为契约（第二优先）

- API 返回结构、错误码、鉴权行为必须稳定：
  - 未登录 401、无权限 403
  - 参数缺失 400
  - 幂等（重复 start/finish 不应产生重复扣减）

> 推荐落点：`src/app/api/**/**.test.ts` 或 `*.integration.test.ts`

### 2.3 关键链路 E2E（只测最小闭环）

- 不追求覆盖全部页面，只测“会造成损失/投诉/数据错乱”的链路：
  - 订阅 → 分配计划 → 今日训练 → 完成 → 进度刷新
  - 支付订单创建/查询

---

## 3. 建议的测试矩阵（什么要测）

### 3.1 订阅（B1）

- subscribed_weeks 变化后 totalCredits/estimated end_date 的变化
- start_date 写入时机：第一次 start 才写入
- end_date 仅用于展示，不作为硬过期判定

### 3.2 计划

- 新建阶段：旧实例 archived，新实例 active，执行统计从 0 开始
- 覆盖当前：instance_id 不变，执行统计保留（文案/提示必须一致）

### 3.3 执行

- 外键字段必须是 `instance_id`
- completed 才计入已完成
- skip/abandon 的展示口径（与 `training-execution-self-consistent-spec-v1` 一致）

### 3.4 自动算重量

- RM 模式：自重动作 \(\alpha=1\)，非自重 \(\alpha=0\)
- 百分比模式：不抵扣自重
- 输出取整/下限（不能负数）

---

## 4. 改进建议（可执行）

### 4.1 把“测试当规格”

- 每个核心模块至少有 1 个“规格测试文件”，像文档一样可读。
- 新 bug 修复必须补测试，否则不算真正解决。

### 4.2 把 E2E 压到最小可维护

- 只保留 P0 链路的 3-5 条用例
- 其它场景用单测/集成测试覆盖

### 4.3 建立“改动影响面”提醒

- 改到以下文件/目录时，触发更严格的测试要求：
  - `src/lib/subscriptionCredits*`
  - `src/app/api/execution/**`
  - `src/app/api/plan-lib/**`
  - `src/app/api/payment/**`

---

## 5. 最小质量门槛（建议写进团队规范）

- PR 必须满足：
  - 关键逻辑改动有测试
  - `npm run test` 通过
- 发布前必须满足：
  - `npm run test` + 关键 E2E 通过
