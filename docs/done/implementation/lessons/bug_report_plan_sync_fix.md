# 计划同步问题排查与修复总结 (2026-01-07)

## 1. 问题现象

**现象描述**：

- 教练在"计划编辑器"中看到某动作的推荐重量已自动更新为 **252.3kg**（基于最新
  1RM）。
- 学员在"今日训练"中看到的同一个动作重量仍然是旧值 **42.8kg**。
- 即使教练点击了"更新计划"（保存），学员端数据依然不更新。
- 只有教练端的界面显示是"新"的，但看起来并没有真正存入数据库。

## 2. 排查过程

我们经历了一个由表及里的深度排查过程：

1. **怀疑数据源不同步**：
   - 最初猜测：教练端和学员端可能读取了不同的数据库表，或者存在一个中间同步过程（Sync
     Job）失败了。
   - **验证结论**：通过代码追踪 (`TodayTrainingCard` ->
     `get-instance API`)，确认 **教练端和学员端读取的是完全相同的数据库字段**
     (`coach_plan_instances.training_days`)。这排除了"读取源不一致"的可能性。

2. **锁定"保存"环节**：
   - 既然读取源一致，那么只有一种解释：**数据库里存的通过的确就是旧值
     (42.8kg)**。
   - 这意味着：尽管教练在屏幕上看到了 252.3kg，但这个新数值
     **并没有被正确写入到底层的状态（State）中**，导致点击保存时，提交给 API
     的仍然是并未修改的旧数据。

3. **发现逻辑 Bug**：
   - 深入检查教练编辑页面的代码
     (`src/app/dashboard/students/plan/[id]/page.tsx`)。
   - 聚焦于处理编辑事件的函数 `handleActionSetChange`。

## 3. 根因分析 (Root Cause)

并在代码中发现了一个严重的逻辑错误——**索引概念混淆**：

- **组件传递的是数组下标**：子组件 `PlanDayCard` 传递给父组件的 `dayIndex`
  参数实际上是 **Array Index**（数组下标，0, 1, 2...）。
- **处理函数误用为天数序号**：父组件的处理函数错误地认为这个参数是 **Day
  Number**（第几天），并试图通过逻辑 `d.dayIndex === index + 1`
  去查找对应的数据。

**Bug 触发场景**：

- 当计划中的天数是连续的（第1天、第2天...），且没有删除过天数时，`Array Index`
  和 `Day Number` 存在巧合的对应关系（Index 0 = Day 1），此时 Bug 隐藏不发作。
- **一旦天数不连续**（例如只有第3天和第17天）：
  - 当教练编辑"第17天"（在数组中是第2个元素，Index=1）时。
  - 错误逻辑尝试查找 `d.dayIndex === 1 + 1 = 2`（查找第2天）。
  - 但数组里没有"第2天"，只有"第17天"。
  - **结果**：查找失败，编辑操作被静默忽略。State 没有更新，UI
    上的输入框可能只是暂时显示了输入值（或由自动计算临时渲染），但底层数据未改变。

## 4. 解决方案

修复了所有相关事件处理函数（`handleActionSetChange`, `handleNoteChange`,
`handleAddActionSet`,
`handleRemoveActionSet`），**直接使用数组下标访问**，不再进行错误的搜索匹配。

**修复前（错误逻辑）**：

```typescript
// 错误地尝试去"搜索"天数，假设了 index 和 dayIndex 的关系
const actualDayIndex = newDays.findIndex((d) => d.dayIndex === dayIndex + 1);
```

**修复后（正确逻辑）**：

```typescript
// 直接信任传入的 index 就是数组下标
const actualDayIndex = dayIndex;
if (!newDays[actualDayIndex]) return; // 安全检查
```

## 5. 经验总结

1. **信任数据流**：当读端（学员）表现正常（读到了DB里的值），而写端（教练）表现异常（"保存"了但没变）时，问题通常出在**写操作未成功持久化**，而不是同步管道断裂。
2. **变量命名需谨慎**：`dayIndex`
   这个名字具有歧义，既可以指"第几天"（业务属性），也可以指"数组下标"（程序属性）。在复杂组件传值时，必须明确其含义。
3. **列表操作陷阱**：在处理由此增删改的列表（如训练日程）时，永远不要假设数组索引（Index）与业务ID（ID/DayNum）存在线性关系（index
   = id - 1），必须使用唯一 ID 查找或确定的索引传递。
