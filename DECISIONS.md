# DECISIONS
- `2026-07-19`: 微信小程序训练执行页的组间休息计时必须和训练总时长一样使用绝对时间基准；`deadlineAt` 是运行中的唯一计时来源，前台 tick、`useDidShow` 恢复、storage 重载以及 `+10/-10 秒`都必须从它计算或更新，禁止只依赖后台会暂停的 `setInterval` 逐秒递减 React state。
- `2026-07-16`: 功率分析 AI 解读属于直接展示给用户的纯文本，禁止输出 `*`、`**` 等星号 Markdown 标记。实现必须同时包含提示词格式约束与服务端清洗兜底，不能只相信模型遵守提示；内容用短标题、自然换行和冒号组织。
- `2026-07-16`: 功率分析结果的字幕语言默认跟随客户端系统语言自动选择中文/英文，并允许用户手动覆盖；选择值必须随任务持久化并传给 Worker。位移、速度、功率曲线属于确定性测量结果，不依赖大模型；最终产品决定为只在小程序结果页显示完整可切换曲线，不烧进结果视频。速度需平滑，瞬时正向功率统一按 `有效质量 × g × max(向上速度, 0)` 计算，时间序列降采样后写入 metrics。
- `2026-07-16`: 功率分析器提供“压缩画质 / 原画质”两档；原画质属于付费会员权益，会员同时获得更高的输入视频上限、结果视频下载能力和分析额度。所有权益和限制必须在服务端按 `student_memberships` 实际状态强制执行，并将质量档位持久化到任务后传给 Worker；前端选项只负责展示与引导升级，不能成为唯一权限控制。当前采用可由环境变量覆盖的默认档位：免费 100MB/30秒/5次，基础 200MB/60秒/20次，高级与试用 500MB/120秒/100次。
- `2026-07-15`: 对“痴迷负重引体”这份既有计划，先采用一次性数据对齐：将 7月13日实际训练视为 D1、7月14日为 D2 恢复、7月15日为 D3。暂不据此修改全局“同一天连续提前训练”的自动排期规则，该复杂场景后续单独设计。
- `2026-07-17`: Web 主站镜像发布优先在本机 Docker 可用时执行 `npm run push-docker-ccr` 构建并推送腾讯云 CCR，再由 Keel/K8s 滚动线上服务。除非用户明确要求或本机 Docker 不可用且已获确认，不要把完整 `coachlink` 源码包上传到生产服务器临时目录构建；如临时上传过，必须清理 `/tmp` 中的源码包和解包目录。
- `2026-07-17`: Web 视频上传的浏览器端自动压缩只应用于真正偏大的视频或需要降分辨率的视频；默认体积阈值为 80MB。40MB 级中等视频应直接走预签名直传或既有上传链路，避免先完整 MediaRecorder 转码再上传。所有上传进度 UI 必须保证百分比单调递增；如果压缩结果因收益不足被丢弃并改传原视频，上传阶段也必须从当前进度继续推进，不能回到 0 或低位。
- `2026-07-17`: CoachLink 生产 Nginx 不能只为功率分析放开大文件限制。所有仍经由 Next.js multipart 的视频上传入口必须在 `littlehorse-deployment/coachlink/coachlink.conf` 有专用 location，并与应用侧 200MB 限制保持一致：当前网关使用 `client_max_body_size 220m`、`proxy_request_buffering off`、上传超时 900 秒。已覆盖 `/api/coach/upload-application-media`、`/api/coach/upload-question-media`、`/api/action-lib/upload-demo-video`、`/api/student/action-lib/upload-demo-video`、`/api/execution/upload-set-video`、`/api/training/upload-set-video`、`/api/user/upload-video`。
- `2026-07-15`: Web `/today-training` 与微信小程序今日训练页各自维护一份计划日期计算；任何排期、顺延和恢复日规则修改必须同步核对两端，不能只修一端。当前统一规则为：尚未到排期的推进日保留原排期，只有真正逾期才向后顺延，`totalDelayDays` 永不为负。
- `2026-07-15`: 计划推进到恢复日时，系统必须停留到下一自然日，不能自动跳过；但用户主动点击恢复日之后的第一个训练日时，允许手动提前结束连续恢复日并开始训练。手动提前只能跨过连续恢复日，绝不能跨过任何尚未完成的训练日。
- `2026-07-15`: 直接为用户/学员创建并立即可执行的计划时，若用户未明确指定未来开始日，`start_date` 必须使用北京时间当天，禁止擅自对齐到“下周一”或其他未来日期。小程序计划月历的 `totalDelayDays` 语义只允许非负的向后顺延；当前推进日早于原排期时应保留原排期，不得强制映射到今天并产生负顺延。
- `2026-07-15`: 微信小程序功率分析 multipart 上传不得把 Busboy 的实时 Node stream 直接交给 Supabase Storage SDK；生产已证实该组合可能返回成功但保存 0 字节对象。上传链路必须先流式落临时磁盘，再以有明确长度的 file-backed Blob 写 Storage，并用 Storage `info` 回查最终对象字节数；大小不一致时删除对象且禁止入队。
- `2026-07-15`: 修改已存在的长周期计划时，大模型不得再返回完整 8～12 周计划。后端必须先按周次、D1～D7 或动作名缩小范围，让模型输出“变化日的完整 PlanScript”局部补丁，校验补丁 dayIndex 未越界后再服务端合并；明确修改还应跳过意图/完整性两次 JSON 前置调用。OpenAI 兼容通道断开时，允许使用同一万界方舟 Key 的 Anthropic 端点对当前小段兜底。
- `2026-07-14`: 完整详细长计划的确定性识别必须发生在 `batch-operation` 的前置意图判断之前；命中后固定走修改路径，并跳过意图 JSON 与完整性 JSON 两次模型调用。只在 `runPlanScriptEdit` 内做本地解析仍会被前置万界方舟断连拦住。
- `2026-07-14`: 已经完整写明周/星期/动作/重量/组次的 8～12 周计划不得再让大模型整份抄写。`batch-operation` 应先确定性转成 PlanScript并校验 7 天/周及处方数量；只有无法确定解析的布局才走万界方舟 Anthropic 半周/密集日分段兜底。长计划的成功标准是周数、84 天和原始处方全部保留，不能只以接口 HTTP 200 或最大周数判断。
- `2026-07-05`: 健康探针修复必须同时保留 `/api/healthy` 与 `/api/health` 在 `src/proxy.ts` 的 `PUBLIC_PATHS` 和 API 前缀白名单中；仅保留路由文件不足以避免 Kubernetes liveness/readiness 401。
- `2026-07-14`: 微信小程序训练完成接口成功后，训练执行页必须立即把服务端完成字段合并回当前 execution 并调用 `syncExecutionToCaches`；不能只打开总结弹层，否则总结内容与分享门禁会分别读取 sets 和旧 status，产生“有训练数据但不可分享”的分裂状态。训练热力图的汇总肌群名称必须显式映射到人体 SVG 的细粒度 category，不能用字符串完全相等匹配。
- `2026-07-14`: 微信小程序所有“选择/追加力量动作”入口统一复用 `apps/wechat/src/utils/actionPickerFilters.ts` 的部位、器械与文本匹配规则，不能在即兴训练首选页和训练执行追加弹层各维护一套分类。学员“我的动作”列表必须通过 `canonical_action_id` 补 `canonical_actions.category` 与 `reference_image_url`；个人自定义且未关联 canonical 的动作才使用无图兜底。
- `2026-07-05`: Web 计划负荷强度字段必须兼容历史旧格式。`params["强度"]` 可能是数字 RM，也可能是字符串 `70%1RM`、`70%rm`、`70%`、`5RM` 或 `"5"`；所有读取侧应先走 `normalizeIntensityConfig` / `calcIntensityDisplay` 归一化，不能直接把旧字段 truthy 值当 RM 次数并追加 `RM`，否则会出现 `70%1RMRM` 并阻断具体 kg 自动计算。
- `2026-07-01`: `/api/user/update-profile` 在 Next API 已通过 `getAuthUser` 验证用户身份后，写入 `user_profiles` 应使用 `serviceRoleSupabase` 执行实际查询/更新/插入，避免小程序 Bearer JWT 场景下普通 Supabase client 缺少 Supabase Auth `auth.uid()` 上下文导致 RLS/权限错位。前端调用方不能吞掉该接口的 `message`，否则注册页只会显示泛化的 `基础档案保存失败`，不利于快速定位字段/约束问题。
- `2026-07-01`: 微信小程序 `toolbox/power-analysis` 应沿用现有工具页的原生导航与更紧凑的纵向密度，不再保留自绘高顶栏。返回入口优先交给小程序原生导航，页面内容区的标题卡、模式卡、视频区和底部按钮应向 `streetlifting/index/calculator` 的紧凑手感靠拢。
- `2026-07-01`: 微信小程序 `streetlifting` / `toolbox` 的游客可访问入口必须遵守一条清晰边界：只读公共数据（如街健统计、社区榜单、地点列表、地图点位、公式表）应直接开放，不应被统一 API 鉴权误拦；需要写入、上传、生成个人结果的动作（如开始功率分析、保存力量历史、提交/认领社区数据、新增或编辑地点）则应在前端入口处明确提示“登录后可用”，不能等到请求失败后再给用户模糊报错。
- `2026-07-01`: 微信小程序 `streetlifting` 力量计算器在未登录时，必须把“需要登录”与“公式缺失/加载失败”区分开。未登录用户可以浏览页面和填写参数，但点击计算或查看个人历史/趣味排名时，应直接给出登录引导，不能再用 `未找到对应公式` 这类误导性提示替代真实原因。
- `2026-07-01`: WeChat 小程序今日训练首页要明确区分三种状态：未登录是访客态，只展示登录与公开浏览；已登录无计划是空计划态，个人训练入口集中在上方 `今天重点` 卡中；已登录有计划是执行态，展示当前计划、整体计划进度、可展开日历和当天安排。不要在空计划态再叠加旧的 `训练入口` 面板，也不要在访客态同时在 hero 和列表重复同一个找教练 CTA。
- `2026-06-25`: Web 教练端学员计划 `AI 修改器` 遇到动作库不存在的新动作时，不能直接失败，也不能把新动作硬匹配到相似旧动作。`plan_script` 引擎应保留用户指定动作名并生成 `pending:` 临时动作，交给既有“确认并映射动作”流程，由用户选择新建动作或映射已有动作后再应用计划。
- `2026-06-23`: Web 教练端 `AI 生成计划 / AI 生成下一阶段` 的单次 phase 长度不能直接等于 `coach_subscriptions.subscribed_weeks`。`subscribed_weeks` 只表示长期已购权益；本次生成周期应优先跟随所选模板/骨架本身的周数，若无模板则只生成保守的短 phase，避免把 4~16 周模板机械扩展成 40 周长计划。
- `2026-06-23`: 对于教练端学员计划里的 AI 负荷调整，产品优先采用“全局 1RM 实时调整”单模式，不单独保留“只改当前 phase 处方重量”作为主路径。前提是当前计划负荷本身与动作级全局 `reference_1rm` 强相关；因此学员反馈“太重/太轻”时，优先回写 `student_actions.reference_1rm`，再让依赖该 1RM 的处方重量实时重算。实现时仍需保留两个保护规则：固定重量处方不要被误重算，且每次 1RM 自动调整都应记录调整原因/幅度，便于回溯与撤销。
- `2026-06-23`: “重量”不是单一能力，而是一个多能力字段。至少要同时支持三种来源：1) 直接写死固定重量；2) 按 RM / %1RM / recommendedLoad 自动计算并回填；3) 通过调整动作级全局 `reference_1rm` 联动重算计划。产品决策上，“学员反馈太重/太轻”的默认主路径仍优先走全局 1RM 调整；但“问卷刚填完、需要把已知重量直接腾到计划里”等场景，必须保留直接填重量能力，不能被 1RM 模式完全替代。
- `2026-06-23`: Web 教练端 `计划 AI 修改器` 的“重量多能力”协议采用双结构化出口：1) `oneRmAdjustments` 负责动作级全局 `reference_1rm` 调整；2) `loadAdjustments` 负责当前计划内的固定重量 / RM / %1RM 小范围调整。这样“反馈驱动降 1RM”和“问卷已知重量直接回填计划”走不同能力，不再强依赖整份计划脚本重写。
- `2026-06-21`: APP 迁移文档体系与测试账号索引采用本地可复用资产包：新增 `skill-factory/coachlink-mobile-app-migration/` 作为多文件迁移技能，`docs/test-accounts/APP-DEV-TEST-ACCOUNTS.md` 作为正式账号清单；其中 `skill-factory` 保持在 `.gitignore` 中不入 Git，以便复用但不污染主仓库历史。

# 训练月历采用“日期事件桶 + 动态压缩/顺延” (`2026-07-18`)

- 计划 Day 表示逻辑执行顺序，自然日期表示实际/计划事件容器；两者不再强制一对一。
- 每个自然日期必须支持存放多个训练 plan Day。若同日完成 D5 与 D7，月历紧凑文案显示 `D5 · D7`；中间 D6 纯休息日只参与后台逻辑指针推进，学员前端任何位置都不展示，不显示 `D5-D7`，避免误导为 D6 也完成了训练。
- 延迟场景：原应训练而未完成的自然日显示 `顺延 -> Dn`，直到实际完成日显示 Dn；历史顺延标记保留用于解释拖延。
- 提前/加练场景：同日完成多个逻辑训练日后，中间纯休息日随逻辑指针跨过并从前端时间轴消失，下一自然日直接从后续 Day 继续，例如同日完成 D5、D7 后次日显示 D8。只有正常到达、尚未被跨过的休息日才显示 `Dn 休`。
- 每次 execution 完成/跳过或进度变化后，未来排期必须从首个未解决 Day 重新连续计算。延迟使未来向后移动，提前完成使未来向前压缩；不得因仅移动已完成 Day 而遗留空白日期。
- 历史实际完成日期以云端 execution 时间为权威且不可重排；日期冲突必须聚合为数组/事件桶，禁止使用 `Map<dateKey, singleDayIndex>` 后写覆盖。
- 小程序训练入口与服务端采用同一休息日跨越权限：若当前严格进度起连续为纯休息日，用户可主动打开其后的第一个训练日并正常执行；该许可不等于自动推进，且不能跨过任何训练日。入口不得再因为目标 Day 不等于严格进度 Day 而一律附加 `readOnly=1`。
- 休息日是否从月历隐藏只能由后续训练 Day 的真实 execution 锚点决定，不能由 `progressDayIndex`、日历选中项或只读预览决定。用户仅查看后续训练日时，前一个未被真实执行跨过的休息日仍须占用独立自然日期并显示 `Dn 休`。
# Web AI 计划修改器采用“当前消息路由 + 隔离草稿” (`2026-07-19`)

- 多轮会话的本轮意图只能根据当前用户消息判断；历史消息仅用于理解指代，不得把历史修改命令再次作为可执行指令。
- “刚才改了什么/哪几周/为什么”等查询必须读取当前计划草稿和累计结构化 diff，只回答，不允许进入任何 PlanScript/code 修改引擎。
- AI 生成结果在确认前必须停留在弹窗独立 draft，不得写父编辑器状态或触发页面 autosave；“确认应用”是唯一提交边界。
- 修改完成必须产生可读助手摘要和可展开完整差异，并进入真实对话历史。后续 refinement 基于当前 draft，累计 diff 始终相对首轮基线。
- Web 计划 AI 修改默认使用 `auto` 引擎，优先 PlanScript 局部补丁。长计划必须在完整自然周边界分段，禁止按任意 N 个训练日把同一周拆开；默认每段最多 2 个完整周、约 8k PlanScript 字符、7000 输出 token。解析失败先纠偏、再用独立 fallback 模型、再缩成逐周补丁；含有效范围内容时只丢弃边界外回显，不得整单失败。
- “每周 135 改成 146”等明确周内排期搬移优先走确定性规则，不调用 LLM。执行前必须验证每个目标周的源日确为训练日，且新增目标日没有非源训练内容；验证通过后按位置顺序搬移动作、备注和处方，原源日转为休息日。无法安全确定时才交给完整周 AI scope，且该 scope 必须包含休息日。
- AI 修改历史按资源 scope 持久化，不只保存在浏览器内存；每条历史必须包含对话、基线快照、草稿快照与累计结构化 diff，才能可靠恢复并在旧内容上继续修改。
- `applied` 历史视为不可变版本；从已应用历史继续时必须 fork 为新的 `draft`，不得覆盖原记录。恢复的历史基线与当前页面计划不一致时必须提示用户检查差异。
- “确认应用”同时把历史状态标记为 `applied`。历史 API 的认证权威是 NextAuth session；服务端使用 service role 访问 RLS 表时，所有读取、更新和插入必须显式绑定 session `userId`，不得信任客户端提交的 user_id。
- 明确的周内排期搬移属于封闭域命令：本地先解析为结构化操作，再对全目标范围做前置校验并原子执行。只要操作已被识别，成功或校验失败都必须 terminal；失败时追问用户，禁止回落到 LLM 生成脚本或代码。
- 周排期语言识别必须由确定性解析器和 PlanScript scope 共享同一判定函数，避免两套正则漂移。“训练周 / 每个训练周 / 每一训练周”等表达与“训练日 / 每周”同等处理。
- AI coding 的可靠性目标不应模仿“一次生成完整计划文本”，而应采用工具循环思想：LLM 只负责把歧义语言翻译为受限的 `PlanEditCommand`，域执行器负责查询、验证、原子修改、diff 与验收；模型输出不能成为计划数据的直接权威来源。
- 打开 AI 修改历史是只读行为，不得创建记录、更新 `updated_at` 或自动 fork。恢复未完成草稿后，只有用户发送新消息或执行明确写操作才更新原草稿；打开已应用历史后，只有用户发送第一条新消息时才创建新分支。已应用历史不得再次执行“确认应用”。
