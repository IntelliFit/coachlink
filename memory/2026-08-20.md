- 用户指出每次点击学员“更新计划”后日期/进度容易变乱。审计确认 Web、小程序、创建/激活/AI 入口的 start_date 与 revision 行为不完全一致，且数据库 single-current trigger 会在应用对账前先把旧实例归档为 `replaced_counted`。
- 新增显式 `revisionOfInstanceId`：已有 execution 的更新由服务端校验旧实例、读取 completed/abandoned 记录、从旧 `start_execution_day` 之后找下一未完成训练日，并以订阅真实 start_date/旧实例 start_date 作为 D1。客户端传入的周/日不能让 revision 跳过真实进度；有 in_progress execution 时直接阻止更新。

- 小程序计划编辑自动保存遇到有历史的内容变化时会创建一次 revision、切换到新 instance ID 并清空当前 revision 的 execution 映射，避免后续每次输入继续从旧实例生成版本；模板覆盖路径也统一使用 revision。

## Fkj 训练视频上传报 FormData 解析失败

- 用户提供的客服会话截图显示昵称为 `Fkj`。未做截图外账号反查。
- 9 秒训练视频上传时，小程序弹出 `Failed to parse body as FormData.`。代码链路为训练执行页 `Taro.chooseVideo` → `executionService.uploadSetVideo` → 对 <=8MB 文件使用 `Taro.uploadFile` multipart → `/api/execution/upload-set-video` 的 `req.formData()`。
- 结论：错误发生在服务端解析 multipart 请求体阶段；不能归因于视频内容、50MB 单文件限制、储存额度或用户权限。最可能为旧小程序包的一次性 multipart 上传兼容问题或中间代理丢失/改写 multipart boundary。
- 7 月已有分片上传修复历史（`3cfda755`、`a098892a`、`6479be00`、`a84b57a8`、`6e024db0`）。本轮已在 `apps/wechat/src/services/executionService.ts` 移除 <=8MB 的 multipart 快路径，训练组视频统一改走已验证的 768KB `application/octet-stream` 分片与 COS 合并接口，避开 `req.formData()`。仍需发布正式小程序并按真实账户回归。
