## Web Admin Standalone Credential Login

- User asked to decouple Web admin login from a real phone number so the currently occupied admin phone can be freed for coach/student relationship testing and separate delete-account testing.
- Product intent:
  - Admin should have its own credential and should not keep consuming one of the limited real phone numbers needed for coach/student testing.
  - The user specifically wants to free the phone currently used by admin, then reuse that phone for coach/student registration and account-cancellation verification.
- Fix applied:
  - Added migration `supabase/migrations/20260521_admin_login_credentials.sql` to extend `admin_users` with standalone login fields:
    - `login_identifier`
    - `password_hash`
    - `is_active`
    - `updated_at`
    - `last_login_at`
  - Added standalone admin credential helpers/API:
    - `src/lib/adminCredentials.ts`
    - `src/app/api/admin/credential/route.ts`
    - `src/app/api/admin/credential/entity.ts`
  - Added standalone admin login page:
    - `src/app/admin/login/page.tsx`
  - Updated NextAuth credentials auth so admin can log in with `adminLogin + adminPassword` while preserving the existing normal user auth flows.
  - Updated `src/proxy.ts` so `/admin/*` unauthenticated access goes to `/admin/login`, and authenticated admins visiting `/admin/login` are sent into admin pages.
  - Updated `src/app/admin/settings/page.tsx` to:
    - Save the standalone admin login identifier/password
    - Show currently bound phone/email
    - Offer a phone unbind action once the standalone admin credential is configured
  - Updated `src/app/api/user/unbind-contact/route.ts` so an admin with a configured standalone admin credential can unbind phone even if no phone/email/wechat login remains on the normal user account.
- Intended operator flow:
  1. Use the old admin login once.
  2. Open `/admin/settings`.
  3. Save the new standalone admin credential.
  4. Unbind the old admin phone there.
  5. From then on, use `/admin/login` for admin access and reuse the freed phone for coach/student/delete-account tests.
- Verification:
  - No browser/manual verification or full command sequence was run because the local workspace preference says not to auto-run them unless explicitly requested.

## WeApp Coach Package Questionnaire Before Payment

- User reported that on coach `枭马葛`, tapping the first package immediately opened a 0.01 WeChat payment QR, while tapping other packages correctly went to the questionnaire first.
- Root cause:
  - The first package matched an existing `inactive` / `pending_payment` subscription for the current user.
  - The coach-profile page had a shortcut that treated selecting that same package as "continue pending payment" and directly called the Huifu/WeChat payment API.
  - Other packages did not match the pending subscription, so they followed the normal questionnaire path.
- Fix applied:
  - Removed the direct-payment shortcut from package selection in `wechat_app/src/discovery/coach-profile/index.tsx`.
  - Package selection now checks the coach questionnaire first, even if a pending/inactive subscription exists.
  - `wechat_app/src/discovery/coach-questionnaire/index.tsx` now reuses the existing subscription id in prepay mode by updating questionnaire/product fields before payment, so the fix does not create duplicate subscriptions for that retry path.
- Verification:
  - Targeted TypeScript transpile check passed for the two touched mini-program files.
  - `git diff --check` passed with only Windows CRLF warnings.
  - No WeChat DevTools/manual UI verification or full build/test was run per local preference.
