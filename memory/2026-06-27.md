## OTel trace naming, service name, and health probe cleanup

- User compared FoodLink Jaeger screenshots with CoachLink screenshots and asked why FoodLink trace results show routes directly while CoachLink only showed `coachlink-web: GET`.
- Finding:
  - FoodLink is a Go/Gin backend and emits route-level operation names like `GET /api/...`.
  - CoachLink's initial Next.js HTTP instrumentation left the root span operation as the default `GET`, so route/path were attributes only and Jaeger search results did not show routes directly.
  - CoachLink's trace hierarchy looks busier because Next.js emits internal middleware/page-resolution spans beneath the HTTP request span. This is expected for Next, but the root span name needed to be more useful.
- Implemented:
  - Added `GET /api/healthy`.
  - OTel incoming HTTP spans now call `span.updateName()` with `METHOD /path` and set `http.route`, `http.method`, and `http.request.method`.
  - `/api/healthy`, `/api/health`, `/api/system/version`, and `/api/public/version` are skipped by both OTel HTTP tracing and the legacy `admin_trace_events` API tracing path.
  - Service naming now prefers `APP_NAME`, matching FoodLink `app.name -> service.name`; `OTEL_SERVICE_NAME=coachlink-web` is treated as a legacy placeholder and ignored.
  - Default service names are `coachlink-backend-main` for production-like envs and `coachlink-backend-dev` for dev/local/test.
  - Invalid all-zero OTel trace ids are ignored so health responses do not emit fake `x-trace-id` headers.
  - Updated `docs/done/system-design/observability-otel.md` with the `APP_NAME=coachlink-backend-main` Apollo mapping and route operation behavior.
