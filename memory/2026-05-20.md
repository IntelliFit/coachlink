  - `HUIFU_SETTLEMENT_PROCESS_INTERVAL_MS` and `HUIFU_SETTLEMENT_RECONCILE_INTERVAL_MS` are optional overrides; set either to `0` to disable that in-process job.

## Payment Landscape Review

- User asked which payments exist besides coach subscription and how they should be handled.
- Current code paths observed:
  - Coach subscription / renewal: should use Huifu-backed platform collection plus delayed balance-payment settlement to coach; this is the only currently hardened split path.
  - Student membership / AI quota pack / storage pack: platform self-operated product. Current mini-program WeChat path uses Huifu collection with `student_membership`; Web membership path still has an older direct-Alipay implementation. No coach split is needed.
  - Coach content single purchase (`content_purchase` / guest purchase): current direct-Alipay path credits coach wallet after payment through `contentPurchaseFulfillment`; this is coach revenue and should eventually be moved to the same Huifu settlement ledger/delay/refund model if it remains paid coach content.
  - Knowledge subscription creation API currently creates/updates `knowledge_subscriptions` from an `order_id`; it should be treated as platform self-operated membership unless it unlocks coach-owned paid content. It should not activate merely from a client-provided order id without a verified paid order.
  - Legacy coach manual/QR/payment-confirmation flows still exist for historical/manual fallback but should not be the primary online payment path for coach subscription because they cannot provide reliable platform escrow, automated refund, or split reconciliation.
- Recommended policy:
  - Any product whose revenue belongs to a coach should enter the Huifu split/settlement/refund ledger.
  - Any product whose revenue belongs entirely to CoachLink can stay platform-account-only with original-route refund, no split.

## Coach Content Purchase Settlement Implementation

- User confirmed the policy: all money related to coaches, including paid coach-written content, should use the same split model as subscription fees.
- Implemented backend rule changes:
  - Paid `content_purchase` now resolves content coach/price from the database and is routed through Huifu when the coach has a fully opened Huifu account.
  - Payment success unlocks the content immediately, but coach wallet income is delayed until Huifu balance-payment settlement succeeds.
  - The existing `coach_subscription_settlements` ledger is reused as a coach-owned revenue settlement ledger, with `order_type = content_purchase` identifying paid content.
  - Huifu notify/query compensation now handles `content_purchase`.
  - Refund handling now treats content purchase as coach-owned revenue: if the coach share has been transferred, it attempts Huifu balance-payment refund/reversal first, then refunds the original collection and marks the content purchase refunded.
  - Coach overview/revenue-detail APIs now count content-purchase revenue from wallet income after settlement, not from source payment success.
  - Guest direct content payment is disabled by routing guests to login first, because guest payment cannot reliably bind entitlement or settlement state.
  - Web paid-content purchase UI now accepts Huifu `payInfo`; if Huifu returns a QR/pay URL, the dialog renders an Alipay scan-to-pay QR and then sends the user to the payment status page for confirmation/unlock.
