## Coach Subscription Entitlement Model

- Context: user investigated student `18115072586` / nickname `枭马葛` and coach `刘三乐`; the mini-program "今日训练" page showed a personal/self plan while the user believed there was an active coach subscription with remaining time. The page also previously showed renewal/expired prompts that conflicted with a visible "剩余45天" subscription display.
- Product conclusion:
  - `coach_subscriptions.subscribed_weeks` is purchased coaching/programming service weeks, not pure calendar days and not a simple fixed session coupon.
  - Training frequency determines how many planned training days exist inside a served week; frequency may change between plan phases.
  - Consumption must be evaluated at the subscription level across plan instances under the same `coach_subscription_id`, not by looking only at the current active plan.
  - `coach_plan_instances.status='archived'` must not itself mean "does not consume subscription". Archived plans that were actually served usually consume entitlement unless explicit metadata says otherwise.
- Decision recorded:
  - Add explicit plan-instance entitlement metadata:
    - `archive_reason`
    - `entitlement_consumption_policy`
    - `entitlement_consumption_note`
  - Supported policies:
    - `count_service`: count completed executions on/after this subscription start.
    - `count_all_history`: count imported/pre-subscription completed history too.
    - `no_charge`: exclude this plan instance from subscription entitlement consumption.
  - Supported archive reasons include `served_phase`, `replaced_counted`, `replaced_no_charge`, `discarded_no_charge`, `legacy_import`, `student_removed`, `system_cleanup`, and `other`.
  - When a plan is replaced:
    - If the old plan has completed executions, default to `replaced_counted + count_service`.
    - If the old plan has no completed executions, default to `discarded_no_charge + no_charge`.
- Intended implementation:
  - Migration: `supabase/migrations/20260517_plan_instance_entitlement_policy.sql`.
  - Shared helper: `src/lib/subscriptionEntitlement.ts`.
  - Carryover calculation: `src/lib/subscriptionCarryover.ts` should count historical plan phases with explicit entitlement policy and ignore pre-subscription completions unless policy is `count_all_history`.
  - Subscription check/list/expiry flows should include archived historical plan instances for consumption, but use the latest non-archived instance as the current cadence source.
  - Manual archive, active-plan replacement, manual plan creation, immediate AI creation, and delayed AI activation should archive old plans with explicit counted/no-charge entitlement metadata.
  - Student/coach plan-history APIs should return `total_training_days`, `plan_span_days`, archive metadata, completion stats, and derived end dates.
  - Student plan-history Web/WeApp copy should say "共 X 个训练日", not "共 X 天", to avoid confusing training-day count with natural calendar span.
- Verification status:
  - Full lint/typecheck/build/test and UI verification were intentionally not run because the local developer preference is to skip automatic verification unless explicitly requested.

## Payment Split / Settlement Audit

- Task: review coach subscription payment split, Huifu balance payment, coach onboarding, wallet credit, and 7-day refund protection.
- Current implementation shape:
  - Mini-program coach subscription payment creates Huifu JSPay order.
  - Paid notify/query fulfills subscription and immediately attempts Huifu balance payment to coach net share.
  - Local wallet/platform revenue credit is tied to `coach_subscription_settlements` split success.
  - Coach Huifu onboarding and Huifu withdrawal surfaces exist.
- Main risks:
  - Huifu refund/balance-payment refund not implemented.
  - 7-day protection is currently only local wallet withdrawal lock, not delayed remote disbursement.
  - Web coach-subscription payment path can still use legacy order types and may bypass split ledger.
  - Reconciliation for uncertain Huifu states is incomplete.
- Product decision:
  - If funds must remain undistributed during the refund window, delay Huifu balance-payment disbursement until `paid_at + 7 days`, or switch to Huifu delayed split with transaction confirm.
