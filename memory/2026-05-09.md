- User asked for an independent investigation of the current payment system and Huifu split-settlement system, specifically to judge whether the whole payment / split-payment chain is safe.
- Targeted audit conclusion:
  - The system is not yet safe enough to call "no problem" for production money flow.
  - The WeChat mini-program coach-subscription payment path is comparatively solid: it creates `coach_subscription(_renew)` Huifu orders, requires coach `huifu_id + huifu_open_status='opened' + huifu_card_token`, verifies Huifu notification content/signature, and only credits coach wallet after Huifu balance split detail exists.
  - The settlement ledger `coach_subscription_settlements` exists and is used as the remote-call idempotency guard; wallet credit for strict `coach_subscription(_renew)` orders refuses missing split detail.
  - Critical risk: Web Huifu Alipay coach-subscription creation still stores legacy order types `subscription` / `subscription_renew`, while Huifu notify/query split execution only runs for `coach_subscription` / `coach_subscription_renew`. This can skip the Huifu split and locally credit the full gross payment to the coach wallet.
  - Critical risk: `/api/payment/alipay/return` directly marks browser-return orders as `paid` and fulfills them without signature verification or server-side gateway query. Return URLs must not mutate money/business state.
  - Refund risk: `/api/payment/alipay/refund` always calls direct Alipay refund SDK and does not branch by `payment_provider`, so Huifu-paid coach-subscription refunds are not production-ready.
  - Operations risk: ambiguous Huifu split exceptions can leave settlement rows in `processing`. There is an admin-only manual retry endpoint, but no visible automatic reconciliation/query job or admin list surface to discover and resolve stuck rows.
  - Broken-link risk: mini-program/service helpers and proxy allowlist reference `/payment/start`, but only `/payment/[id]` exists under `src/app/payment`, so some direct payment fallback links are broken.
- Recommended first fixes:
  - Normalize Web coach-subscription orders to split-required `coach_subscription(_renew)` or make all split/credit branches detect Huifu coach-subscription by `payment_provider + order_data.coachId`.
  - Change `alipay/return` to redirect/status-only; fulfillment should be signed notify or server-side query only.
  - Add provider-aware Huifu refund handling.
  - Add a reconciliation/admin discovery flow for `coach_subscription_settlements.status='processing'`.
  - Implement `/payment/start` or remove/replace the broken references.
