## WeChat Mini-Program Dark Theme Binding Fix

- Problem: toggling dark mode in `/me/profile/index` only changed the system status bar/navigation bar; page content (background, cards, text) stayed light.
- Root cause: `.app-root.theme-dark` lives inside the App component and cannot reach `<page>` nodes, which are siblings in the WeChat Mini Program DOM. The `theme-dark` class was never applied to individual page roots.
- Fix:
  - Added a reusable batch script `wechat_app/scripts/add-theme-class-to-pages.js` that reads `wechat_app/src/app.config.ts`, finds every page entry file, inserts `const { effectiveTheme } = useTheme()` and a `theme-${effectiveTheme}` class on each page-level root JSX element.
  - Ran the script over all 117 page files; manually patched `wechat_app/src/training/actions/index.tsx` (no className) and `wechat_app/src/training/today-training/index.tsx` `renderLoading` helper (nested return).
  - Updated `wechat_app/src/app.scss` so `.theme-dark` itself sets `background: var(--bg-page)` as a catch-all for any page root that now carries the class.
- Verification:
  - `npm run build:weapp` succeeded.
  - Babel syntax check on all modified `.tsx` files passed.
  - WeChat DevTools automation on port 9421 navigated to `/me/profile/index`.
  - Initial screenshot showed dark mode applied to profile page; tapping the theme toggle switched the whole page to light mode.
  - `mrc screenshot` became flaky after the first capture (known DevTools automation limitation); no runtime errors were logged.
- Artifacts:
  - `screenshots/weapp-theme/profile-light.png`
  - `screenshots/weapp-theme/profile-after-toggle.png`

## WeChat Mini-Program BottomNav Switch Animation

- Problem: the active item in `BottomNav` had a nice entrance animation on first load, but switching tabs felt instant because each page re-mounts its own `BottomNav` and the active state is applied immediately on mount (CSS transitions do not run for initial styles).
- Fix in `wechat_app/src/components/BottomNav.tsx`:
  - Added a `mounted` state initialized to `false`.
  - On mount, `syncCurrentPath()` runs first, then a `setTimeout(..., 0)` flips `mounted` to `true`.
  - Rendered active state is forced to `false` while `mounted` is `false`; once `mounted` becomes `true`, the active item transitions from the inactive state to the active state, triggering the existing CSS `transition`.
- Verification:
  - `npm run build:weapp` succeeded after the change.
  - WeChat DevTools automation on port 9421 navigated from `/training/today-training` to `/discovery/index` by tapping the discovery nav icon without errors.
  - `mrc screenshot` remained flaky, so the animation could not be captured as a screenshot sequence, but the navigation path completed and no runtime errors were logged.

## WeChat Mini-Program BottomNav Animation Scope Refinement

- Problem: after the previous `mounted` fix, the active item animated on *every* page mount, including page loads triggered by in-page links (e.g., navigating back to a tab). The user wanted the animation only when switching tabs via the bottom navigation bar itself, and no transition animation on the main page content.
- Fix in `wechat_app/src/components/BottomNav.tsx`:
  - Reused the existing `bottom_nav_switching` storage flag mechanism: `Taro.setStorageSync(BOTTOM_NAV_SWITCH_KEY, '1')` is set only inside `handleNavClick` (bottom nav tap).
  - On mount, the new page’s `BottomNav` reads the flag, removes it, and plays the active-item transition once.
  - In-page navigations do not set the flag, so they do not trigger the nav animation.
  - Navigation already uses `animationType: 'none'`, so the main page content never performs a page transition.
  - Changed the `setTimeout(..., 0)` that flips `playSwitchAnimation` back to `false` into `setTimeout(..., 16)` to guarantee at least one inactive frame before the active state is restored.
