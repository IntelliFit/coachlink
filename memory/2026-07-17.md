## 功率分析 worker/队列归属复核

- 用户询问功率分析是否使用消息队列或 Redis，以及 worker 是独立项目还是当前目录内。
- 复核结论：功率分析代码在当前 `coachlink` 仓库内，worker 入口为 `scripts/power-analysis-worker.mjs`，核心逻辑在 `scripts/power-analysis-worker.ts` / `scripts/power-analysis-worker-cli.ts`，Python 分析器在 `scripts/power-analysis/analyze_video.py`。
- 运行形态是独立进程/独立 Docker 镜像，不是另一个 Git 项目；镜像文件为 `Dockerfile.power-worker`，推送脚本为 `scripts/push-power-worker-ccr.mjs`，npm 命令是 `npm run power-analysis:worker` 与 `npm run push-power-worker-ccr`。
- 队列层使用 `src/lib/taskqueue/*` 抽象；本地可用 memory queue，生产按设计使用 Kafka（`TASK_QUEUE_DRIVER=kafka`、`TASK_QUEUE_BROKERS`、`TASK_QUEUE_TOPIC`）。Redis 不是功率分析任务队列，只是项目其他功能依赖。

## 教练视频上传 Nginx 413 修复

- 用户反馈生产服务器 `ubuntu@154.8.205.78` 上教练上传十几 MB 或几十 MB 视频失败，要求检查 `littlehorse-deployment`。
- 诊断：生产 Nginx 只给 `/api/toolbox/power-analysis/` 放开大文件上传；教练/动作/训练视频 multipart 上传路径仍走通用 `location /`。2MB 未登录探针在 `/api/coach/upload-application-media`、`/api/coach/upload-question-media`、`/api/action-lib/upload-demo-video`、`/api/execution/upload-set-video` 均被 Nginx HTML 413 拦截，功率分析路径返回应用 JSON 401。
- 修复：`IntelliFit/littlehorse-deployment` 提交并推送 `ec9f39c fix: raise CoachLink video upload nginx limits`。`coachlink/coachlink.conf` 现在保留功率分析 520MB 专用入口，并为仍走 Next multipart 的视频上传路径添加 220MB 专用 location、`proxy_request_buffering off` 和 900 秒上传超时；dev 域名同步。
- 部署：已更新服务器 `/etc/nginx/conf.d/coachlink.conf`，`sudo nginx -t` 通过并 reload；服务器部署仓库 `/home/ubuntu/littlehorse-deployment` 已通过本地 Git bundle 同步到 `ec9f39c`，避免服务器 GitHub fetch 卡住导致仓库状态落后。
- 验证：修复后 2MB 探针全部进入应用层返回 JSON 401；25MB 探针到 `/api/coach/upload-application-media` 与 `/api/action-lib/upload-demo-video` 也返回应用 JSON 401，不再被 Nginx 413 拦截。未使用真实登录态写入业务数据。

## Web 视频上传慢与进度回退修复

- 用户提供本地视频 `425aa7b98920c999b842dac6da336da3_raw - 副本.mp4`，大小 `42023706` 字节，反馈 Chrome 登录态上传仍慢且进度条会来回跳/从大到小。
- Chrome 控制已接入并打开 `/dashboard/action-lib`；文件选择时扩展返回 `fileChooser.setFiles failed: Not allowed`，按 Chrome 插件说明需要在 `chrome://extensions` 为 ChatGPT Chrome Extension 打开 `Allow access to file URLs`，所以没有完成真实页面文件写入。
- 代码诊断：18MB 自动压缩阈值会让 42MB 视频先在浏览器端完整 MediaRecorder 转码，显著变慢。若压缩结果收益不足，`prepareVideoForUpload` 返回原视频，而 `actionLibService` / `videoService` 上传阶段按 XHR 原始百分比重新开始，导致进度从压缩阶段高位回退。
- 修复：`AUTO_COMPRESS_THRESHOLD_BYTES` 提到 80MB；`actionLibService.uploadDemoVideo` 和 `videoService.uploadVideoFile` 增加单调递增进度映射，上传阶段从当前进度继续推进。
- 验证：相关单测、lint、typecheck、完整单测与 `npx next build` 均通过；首次 build 因本机 `node_modules` 缺 lock 中已有的 `busboy` / `pdf-parse` 失败，`npm install` 后恢复并通过。
