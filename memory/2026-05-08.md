- **Third fix round** (after user provided full console logs):
    - Log analysis revealed three distinct failures:
      1. `canvas.createImage is not a function` in WeChat DevTools — the Canvas 2D node in DevTools simulator lacks `createImage()`.
      2. QR code backend returned HTTP 500 because `getwxacodeunlimit` `scene` exceeded WeChat's 32-character limit (`lid=UUID` = 40 chars).
      3. `writeFileSync:fail the maximum size of the file storage limit is exceeded` when writing image binary to local temp file.
    - Fixes applied:
      - `poster.ts`: `createCanvasImage` now tries `canvas.createImage()` → `wx.createImage()` → `wx.createOffscreenCanvas({ type: '2d' }).createImage()` in that order, so it works on real devices and falls back gracefully in DevTools.
      - Backend `src/app/api/miniapp/qrcode/streetlifting-location/route.ts`: `scene` changed from `lid=${locationId}` to `locationId.replace(/-/g, '')` (exactly 32 chars for a UUID). Added `?format=base64` support so the mini-program can fetch the QR via `Taro.request` with Authorization header instead of `downloadFile`.
      - `wechat_app/src/streetlifting/index/location-share/index.tsx`: `parseScene` updated to handle both old `lid=xxx` format and new 32-char stripped-UUID format, rehydrating the latter back to standard UUID.
      - `wechat_app/src/utils/weapp-canvas-image.ts`: `resolveCanvasImageSrc` now has a third fallback using `Taro.request` with `responseType: 'arraybuffer'` and `Authorization` header, writing the response to a temp file for Canvas use.
      - `wechat_app/src/streetlifting/index/locations/index.tsx`: `handleOpenPoster` now fetches QR base64 via `Taro.request` and image binary via `Taro.request` before generating the poster. If `writeFileSync` fails for the image, it automatically falls back to `Taro.downloadFile`.
    - Build verification: `wechat_app npm run build:weapp` passed, root `typecheck` passed, root `npx next build` passed.
