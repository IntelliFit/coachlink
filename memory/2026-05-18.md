- API facts from the user's docs:
  - User onboarding: personal user open `/v2/user/basicdata/indv`; business open `/v2/user/busi/open` with `card_info + cash_config`; response can include `token_no`.
  - Balance payment: `/v2/trade/acctpayment/pay`; requires `out_huifu_id`, `ord_amt`, `risk_check_data`, and `acct_split_bunch`; split amounts must equal `ord_amt`.
  - Withdrawal: `/v2/trade/settlement/encashment` uses `huifu_id`, `cash_amt`, `into_acct_date_type`, and `token_no`.
  - Docs expose balance-payment refund/refund-query, so Huifu refund support is available conceptually but not yet implemented in CoachLink code.
  - Huifu guide distinguishes real-time split, delayed split using `delay_acct_flag=Y` plus transaction confirm, and post-collection balance payment.
- Interpretation for CoachLink:
  - Current code's balance-payment shape, where `ord_amt` is the coach net share and the only receiver is the coach, is compatible with Huifu docs if the platform commission stays in the platform Huifu account.
  - Current implementation is not true Huifu delayed split; it is post-collection balance payment.
  - Current 7-day refund protection is only a local coach-wallet withdrawal lock. If product policy requires funds to remain in the platform account during the refund window, the balance-payment disbursement itself should be delayed until 7 days after payment, or the integration should switch to Huifu delayed split.

## Huifu Split Current Implementation Review

- Current implemented surfaces:
  - `src/lib/huifuMiniProgramPay.ts`: Huifu config/sign/verify, JSPay creation/query, notify verify, personal user open, business open, account query, balance payment, encashment.
  - `/api/payment/wechat/coach/create`: mini-program coach-subscription order creation with Huifu `T_MINIAPP`, coach Huifu opened/token gate, order type `coach_subscription` / `coach_subscription_renew`, payment provider `wechat`.
  - `/api/payment/wechat/notify` and `/api/payment/wechat/query`: paid-order status update, subscription fulfillment, immediate `executeBalancePayment`, and local wallet/platform revenue credit after split success.
  - `executeBalancePayment`: creates/claims `coach_subscription_settlements`, calls Huifu balance payment for coach net share, stores split state, refuses local wallet credit without split details.
  - Coach onboarding `/api/coach/merchant/open-huifu-account`: personal user open plus business open with `card_info + cash_config`, stores `huifu_card_token`.
  - Coach withdrawal `/api/coach/wallet/huifu/withdraw`: uses Huifu encashment and local 7-day wallet lock.
  - Admin retry `/api/admin/coach-subscription-settlements/retry`: can trigger a real balance-payment transfer when explicitly confirmed.
- Main gaps and risks:
  - Huifu original-payment refund and balance-payment refund are not implemented. Existing refund endpoint still uses Alipay `alipay.trade.refund`, so it is unsafe for Huifu WeChat/Huifu-Alipay orders.
  - 7-day protection currently prevents CoachLink withdrawal only after wallet credit; it does not delay remote Huifu balance payment to the coach.
  - No automated query/reconciliation exists for Huifu balance-payment `P` states, ambiguous exceptions, or Huifu withdrawal processing/failure.
  - Web coach-subscription payment path can create Huifu A_JSAPI/A_NATIVE orders while retaining legacy `subscription*` order types, and downstream code may credit the coach wallet without the Huifu split ledger.
  - Coach business onboarding currently treats Huifu `apply_no`/审核中 without `token_no` as failure rather than a pending state.
- Recommended order:
  - Do read-only config/schema/data verification first.
  - Add safety guards for Huifu refund/Web legacy split before broad live testing.
  - Run one controlled mini-program 1-yuan payment only after accepting that the current code will immediately disburse coach net share.
  - Then implement Huifu refund, delayed settlement policy, and reconciliation jobs.
